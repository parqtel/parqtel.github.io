Internals

Query Reference#

Parqtel implements 91 functions, 12 aggregations, 15 binary operators, and all four label matchers. This page lists the surface and is explicit about where the semantics differ from Prometheus.

Parqtel exposes three query surfaces:

SurfaceUsed forSyntax
ParQLMetricsPromQL-compatible
ParqtelQLLogs and spansLenient boolean filters
PQL pipelinesCross-signal queriesStaged `fetch \

Prerequisites#

  • Parqtel running with data ingested — see Ingest Telemetry.
  • Familiarity with PromQL is assumed, but not required. Start with the Quickstart for a first query.

Two engines, one dispatcher#

Parqtel runs some queries through a fast path and others through a more capable path. A classifier chooses per query:

  • Any aggregation always takes the full expression path. The fast path treats aggregations as per-series downsamplers and mis-parses sum(x) by (l).
  • Any binary operator, or a call outside the legacy function list, also takes the full expression path.
  • Everything else goes through the fast path: parse → plan → execute, with the lowest overhead.

Both paths share the same storage layer, the same limit enforcement, and the same offloading to blocking workers, so behaviour is consistent apart from the documented divergences below.

Label matchers#

metric_name{key="value"}     # exact
metric_name{key!="value"}    # not equal
metric_name{key=~"re.*x"}    # regex match
metric_name{key!~"re.*x"}    # regex non-match

Regexes are compiled once per request and shared across every row examined, rather than rebuilt per row.

Aggregations#

sum · avg · min · max · count · stddev · stdvar · count_values · topk · bottomk · quantile · group

Both by and without are supported, in either position:

sum by (service, method) (rate(http_requests_total[5m]))
sum(rate(http_requests_total[5m])) by (service)
topk(10, http_requests_total)
quantile by (le) (0.95, http_request_duration_seconds_bucket)
sum without (instance) (http_requests_total)

Range functions#

rate · irate · increase · delta · idelta

rate(http_requests_total[5m])       # per-second average over the window
increase(http_requests_total[1h])   # total growth over the window
irate(http_requests_total[1m])      # last sample's instantaneous rate

Over-time aggregations#

avg_over_time · min_over_time · max_over_time · sum_over_time · count_over_time · quantile_over_time · mad_over_time · stddev_over_time · stdvar_over_time · last_over_time · present_over_time

Prediction and change detection#

changes · resets · deriv · predict_linear · holt_winters · double_exponential_smoothing

predict_linear(node_filesystem_avail_bytes[6h], 4 * 3600) < 0
resets(process_start_time_seconds[1h]) > 3

Label manipulation#

label_replace(up, "host", "$1", "instance", "([^:]+):.*")
label_join(up, "target", "/", "service", "instance")
label_del(http_requests_total, "debug_flag")

Ranking and sorting#

sort(http_requests_total)
sort_desc(sum by (service) (rate(http_errors_total[5m])))
sort_by_label(http_requests_total, "service")
sort_by_label_desc(http_requests_total, "service")

Absence detection#

absent(up{job="checkout"})
absent_over_time(node_up[10m])

Histograms#

histogram_quantile · histogram_count · histogram_sum · histogram_avg · histogram_stddev · histogram_stdvar · histogram_fraction

histogram_quantile(
  0.95,
  sum by (le, service) (rate(http_request_duration_seconds_bucket[5m]))
)
↗

histogram_quantile works in interactive queries but not in alert rules. The alert loop uses the fast path, not the full expression engine. Use _sum rate proxies for latency alerting. See Alerting.

Binary operators and set operators#

Arithmetic: + - * / % ^ Comparison: == != > < >= <= Set: and or unless

Vector matching modifiers: on(...), ignoring(...), group_left, group_right, and the bool suffix.

# Error ratio, matched on service
sum by (service) (rate(http_errors_total[5m]))
  / on (service)
sum by (service) (rate(http_requests_total[5m]))

# Only return series whose paired series is also present
http_requests_total and on (service) up == 1

# Keep right-hand labels
node_load1{job="node"}
  * on (instance) group_left (env, dc)
node_uname_info{job="node"}

Semantic divergences#

Behaviours that differ from upstream Prometheus. Each is a characterised, deliberate difference rather than accidental drift.

DivergenceDetail
rate skips edge extrapolation on the expression pathIt passes a zero window, so rates computed inside a binary-operator expression are not extrapolated to the window edges. The same query without a binary operator will be extrapolated.
timestamp(x)Returns the evaluation timestamp, not the sample's own timestamp.
derivA two-point slope, not the ordinary-least-squares fit Prometheus uses.
count_values, quantile, topk, bottomkIgnore by / without.
@ modifierRejected outright rather than parsed and ignored.
Duration unitsExclude Prometheus' y and M.
log(v, base)Absent — use log2 or log10.
Also absentts_of_*_over_time, limitk, limit_ratio, info.
↗

Because two engine paths exist, a few functions behave differently depending on which path a query selects. The divergences above account for the known cases.

Instant queries and bare range functions#

An instant query (/api/v1/query) that is exactly a range function over a selector — for example rate(http_requests_total[5m]) — selects the fast plan path. In v0.3.1 that path does not downsample instant queries, so the response is the newest raw sample, not the computed rate. Two workarounds:

  • use a range query (/api/v1/query_range), which always supplies a step; or
  • wrap the expression so it takes the expression path, e.g. sum(rate(http_requests_total[5m])).

This affects instant queries only. The console and Grafana range panels are not affected, and sum_over_time/count_over_time/avg_over_time always use the expression path.

Result limits#

SettingDefaultBehaviour when exceeded
query.max_series1000Silent truncation. No error, no error status, no warning field — the response is simply shorter.
query.max_samples_per_series10000Silent truncation.
⚠

⚠ Clients must detect truncation themselves. Compare totalSeriesCount (the pre-truncation matched count) against the number of series returned, and check volume_summary. Logs and traces do return an explicit truncated boolean.

Because two engine paths exist, they keep different samples when truncating: the expression path keeps the oldest N, while the fast path keeps the first N in scan order. Both paths enforce both limits.

Limits that do produce an error, by contrast:

ConditionStatus
Request body exceeds ingest.max_body_size413
Request exceeds query.timeout_secs408
Plan validation failure400

Logs — ParqtelQL#

Log search uses a lenient boolean filter grammar.

severity>=INFO
severity>=ERROR body:/timeout/
service.name="checkout" -severity:DEBUG
curl "http://localhost:8080/api/v1/logs?query=severity%3E%3DINFO&start=1700000000&end=1700003600"

query is required; start and end are Unix seconds. See the HTTP API Reference for all log endpoints and parameters.

Traces#

Trace search returns spans, each carrying its trace_id. Filter with the q predicate — the other documented filter parameters are accepted but not honoured.

curl "http://localhost:8080/v1/traces/search?q=service.name%3D%22my-web-app%22&limit=20"

start/end (Unix seconds) and limit are optional; the server also accepts trace_id to fetch a single trace.

Pipelines#

A pipeline stages a query across all three signals:

fetch logs | filter severity>=ERROR | correlate traces window=2s

Stages: fetch → filter → parse → stats → correlate.

curl -X POST http://localhost:8080/v1/search \
  -H "Content-Type: application/json" \
  -d '{
    "query": "fetch logs | filter severity>=ERROR | correlate traces window=2s",
    "start": 1700000000,
    "end": 1700003600
  }'

Worked examples#

Service error ratio#

sum by (service) (sum_over_time(traces_service_errors_total[5m]))
  /
sum by (service) (count_over_time(traces_service_requests_total[5m]))

Request rate per service#

sum by (service) (count_over_time(traces_service_requests_total[5m])) / 300

Average request duration#

sum by (service) (sum_over_time(traces_service_duration_ms[5m]))
  / sum by (service) (count_over_time(traces_service_duration_ms[5m]))
↗

The span-metrics RED bridge writes one gauge sample per server span (requests=1, errors=0/1, duration=ms). The _total suffix is a naming convention, not cumulative-counter semantics, so use _over_time functions rather than rate(). There is no latency histogram, so a true P95 requires instrumenting one yourself.

Disk will fill within 4 hours#

predict_linear(node_filesystem_avail_bytes[6h], 4 * 3600) < 0

Services with no successful requests#

absent(up{job="checkout"})

Troubleshooting#

SymptomCauseResolution
Query returns fewer series than expectedSilent truncation at query.max_series.Compare totalSeriesCount with returned series; aggregate or raise the limit.
An instant query returns nothing for old dataOutside the 5-minute lookback.Use /api/v1/query_range.
rate behaves differently inside a binary expressionNo edge extrapolation on the expression path.Documented divergence. Avoid relying on edge extrapolation.
topk / quantile ignore byDocumented divergence.Apply the aggregation outside, or accept the grouping.
@ modifier errorsRejected outright.Remove it and use explicit timestamps.
histogram_quantile fails in an alert ruleNot available on the alert path.Use a _sum rate proxy.
A range query returns one fewer sample at the endFinal partial step is not evaluated — matches Prometheus.Extend end by one step.
log(v, base) not foundNot implemented.Use log2 or log10.
Request returns 408Exceeded query.timeout_secs.Narrow the range, aggregate, or raise the timeout.
