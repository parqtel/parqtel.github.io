Query Functions

Parqtel implements 91 functions, 12 aggregations, 15 binary operators and all four label matchers. This page lists the surface and is explicit about where the semantics differ from Prometheus.

ℹ

A conformance corpus of 88 → 98 cases gates semantic changes to the query engine, so the divergences below are characterised behaviour rather than accidental drift.

Two engines, one dispatcher

Not every query goes down the same path. A classifier decides per query:

  • Any aggregation always takes the AST path. The legacy engine treats aggregations as per-series downsamplers and mis-parses sum(x) by (l).
  • Anything containing a binary operator, or a call outside the legacy 20-function list, also takes the AST path.
  • Everything else goes parse → QueryPlan → execute — the fast path with the lowest overhead.

Both paths share the same storage layer, the same limit enforcement and the same blocking-pool offload. The AST path's entire CPU stage runs inside a single spawn_blocking (regression-tested by test_query_evaluation_does_not_block_the_async_worker); Parquet decode sits behind a 16-permit semaphore with the permit acquired before spawning.

⚠

Because two paths exist, a few functions behave differently depending on which one a query selects — see Semantic divergences.

Label matchers

metric_name{key="value"}            # exact
metric_name{key!="value"}           # not equal
metric_name{key=~"re.*x"}           # regex match
metric_name{key!~"re.*x"}           # regex non-match

Regexes are compiled once per request and shared across every row examined, not rebuilt per row.

Aggregations

sum · avg · min · max · count · stddev · stdvar · count_values · topk · bottomk · quantile · group

Both by and without are supported in either position:

sum by (service, method) (rate(http_requests_total[5m]))
sum(rate(http_requests_total[5m])) by (service)
topk(10, http_requests_total)
quantile by (le) (0.95, http_request_duration_seconds_bucket)
sum without (instance) (http_requests_total)

Aggregation groups are keyed by a label fingerprint, and each distinct group's label set is built once rather than per series. Series labels are shared behind an Arc and cloned once per block, not once per step.

Range functions

rate · irate · increase · delta · idelta

rate(http_requests_total[5m])        # per-second average over the window
increase(http_requests_total[1h])    # total growth over the window
irate(http_requests_total[1m])       # last sample's instantaneous rate

⚠

histogram_quantile works in interactive queries but not in alert rules — the alert loop uses the query plan path, not the AST engine. Use _sum rate proxies for alerting on latency.

Binary operators and set operators

Arithmetic: + - * / % ^  ·  Comparison: == != > < >= <=  ·  Set: and or unless

Vector matching modifiers: on(...), ignoring(...), group_left, group_right, and the bool suffix.

# Error ratio, matched on service
sum by (service) (rate(http_errors_total[5m]))
  / on (service)
sum by (service) (rate(http_requests_total[5m]))

# Only return series whose paired series is also present
http_requests_total and on (service) up == 1

# Keep right-hand labels
node_load1{job="node"}
  * on (instance) group_left (env, dc)
node_uname_info{job="node"}

Semantic divergences

Behaviours that differ from upstream Prometheus. Each is characterised by the conformance corpus.

⚠
  • rate skips edge extrapolation on the AST path — it passes a zero window, so rates computed in a binary-operator expression are not extrapolated to the window edges. The same query without a binary operator will be.
  • timestamp(x) returns the evaluation timestamp, not the sample's own timestamp.
  • deriv is a two-point slope, not the ordinary-least-squares fit Prometheus uses.
  • count_values, quantile, topk and bottomk ignore by/without.
  • The @ modifier is rejected outright rather than parsed and ignored.
  • Duration units exclude Prometheus' y and M.
  • log(v, base) is absent — use log2 or log10.
  • Also absent: ts_of_*_over_time, limitk, limit_ratio, info.

Result limits

SettingDefaultBehaviour when exceeded
query.max_series1000Silent truncation. No error, no error status, no warning field — the response is simply shorter.
query.max_samples_per_series10000
⚠

Clients must detect truncation themselves, from totalSeriesCount (the pre-truncation matched count) and volume_summary. Logs and traces do return an explicit truncated boolean. And because two engine paths exist, the two keep different samples when truncating: the AST path keeps the oldest N, the legacy plan path keeps the first N in scan order. Both are enforced on the plan and AST paths alike.

Limits that do error, by contrast: an oversized body returns 413; a request exceeding query.timeout_secs returns 408; plan validation failures return 400.

Logs, traces and pipelines

Metrics PromQL is only one of three query surfaces.

SurfaceGrammarEndpoint
ParqtelQLLenient boolean log/span search: terms, phrases, wildcards, -exclusion, OR/AND/NOT, field operators, ranges, field:* exists, body: contains, severity thresholds/api/v1/logs, /v1/traces/search
PQL pipelinesfetch … | filter … | parse … | stats … by … interval=… | limit | correlate traces|logs window=…POST /v1/search

Log and trace queries are prepared once per request — regexes compiled, needles lowercased — and scanned with an allocation-free ASCII-case-folded substring matcher. Trace predicates are pushed down into the scan before the result cap, so a filter never loses matches to truncation. See the ParqtelQL guide.
