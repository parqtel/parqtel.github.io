Back Up, Restore & Upgrade#

Because Parqtel stores telemetry as immutable Parquet block files, backup is a file copy that is safe to run while the server is live, and restore is a file copy back. This guide covers what to back up, how to restore, and the one upgrade boundary that requires wiping your data.

What is on disk#

The trace directory is derived, not configurable separately: it is always <storage.data_dir>/traces, with its own index.json. Logs have their own data_dir (data/logs by default) and their own index.

ComponentBack up?Why
Parquet blocks✅ Yes — essentialThis is your telemetry. Immutable once written.
Block index⚠️ OptionalA cache, not the source of truth. Speeds startup; rebuilds itself if lost.
Write-ahead log❌ NoEphemeral. A replay is a replay, not a backup. It contains only data not yet in a block.
Configuration✅ YesYour TOML file, rule files, and Helm values.
↗

The block index is self-healing. If it is lost or stale, Parqtel reconciles it against the data directory at startup: unknown block files are adopted, and entries whose file has disappeared are dropped. Backing it up is an optimisation, not a requirement.

Prerequisites#

RequirementDetail
Access to the data directoryFor Docker, the mounted volume. For Kubernetes, the PersistentVolume.
Enough space at the destinationAt least the size of the data directory.
For upgradesThe release notes for your target version — see Release Notes.

Check what you are actually storing before you copy:

curl -s http://localhost:8080/api/v1/stats | jq

Backing up#

Option 1 — Copy the data directory (live)#

Blocks are immutable and never modified in place, so a copy taken while the server runs is consistent. A block being written right now appears as a temporary file and is excluded by the pattern below.

# Docker: copy out of the named volume
docker run --rm \
  -v parqtel_data:/data \
  -v "$PWD/backup:/backup" \
  alpine sh -c 'cp -av /data/. /backup/'
# systemd / bare metal
sudo rsync -a --exclude '*.tmp*' /var/lib/parqtel/data/ /backup/parqtel-$(date +%F)/
sudo rsync -a --exclude '*.tmp*' /var/lib/parqtel/logs/ /backup/parqtel-logs-$(date +%F)/
# Kubernetes: snapshot the PersistentVolume, or copy from the pod
kubectl -n parqtel cp parqtel-0:/data ./backup-data

Option 2 — Filesystem or volume snapshot (preferred)#

Snapshots are atomic and cheaper for large data sets. Any snapshot mechanism works, because the files are immutable.

# Example: AWS EBS snapshot of the volume backing the PVC
aws ec2 create-snapshot --volume-id vol-0123456789abcdef0 \
  --description "parqtel $(date +%F)"

Option 3 — Back up configuration separately#

# Rule files and config
kubectl -n parqtel get configmap parqtel-config -o yaml > parqtel-config.yaml
kubectl -n parqtel get secret parqtel-secrets -o yaml > parqtel-secrets.yaml
helm -n parqtel get values parqtel > parqtel-values.yaml

Backup checklist#

  • [ ] Parquet blocks copied or snapshotted
  • [ ] Log blocks copied (if logs.data_dir is separate)
  • [ ] Configuration file backed up
  • [ ] Alert rule files backed up
  • [ ] Helm values (if applicable) backed up
  • [ ] Restore tested at least once

Restoring#

Restore is the reverse: put the files back and start the server.

# 1. Stop Parqtel
docker stop parqtel

# 2. Restore blocks into the data directory
docker run --rm \
  -v parqtel_data:/data \
  -v "$PWD/backup:/backup:ro" \
  alpine sh -c 'rm -rf /data/* && cp -av /backup/. /data/'

# 3. Start Parqtel
docker start parqtel
# Kubernetes
kubectl -n parqtel scale deploy/parqtel --replicas=0
kubectl -n parqtel cp ./backup-data parqtel-0:/data     # or restore the snapshot
kubectl -n parqtel scale deploy/parqtel --replicas=1

Verify the restore#

# Readiness must pass — it reads block-index metadata
curl -sf http://localhost:8080/ready

# Confirm blocks and rows are visible
curl -s http://localhost:8080/api/v1/stats | jq

# Confirm reconciliation adopted the restored blocks
docker logs parqtel 2>&1 | grep -E 'reconciled|WAL replay'
↗

Deleting the index is safe. If you restore only the Parquet files and not the index, Parqtel rebuilds the index from the block footers at startup. This takes longer on a large data set but loses nothing.

Upgrading#

Standard upgrade (v0.2.0 and later)#

The on-disk format is stable from v0.2.0 onward, so an upgrade is a binary or image swap.

# Docker — replace 0.3.1 with the target release tag
docker stop parqtel && docker rm parqtel
docker run -d --name parqtel \
  -p 8080:8080 -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:0.3.1
# Kubernetes / Helm
helm repo update
helm -n parqtel upgrade parqtel parqtel/parqtel --version <new-version>
kubectl -n parqtel rollout status deploy/parqtel
↗

Watch the startup probe. On start, Parqtel replays whatever the write-ahead log did not flush, and replay time is proportional to unflushed log size. Right after an upgrade this can exceed the default 150-second startup budget. If the pod restart-loops, raise startupProbe.failureThreshold — do not remove the startup probe. See Deploy.

The one breaking boundary#

FromToAction
v0.2.0+any later versionIn-place upgrade.
Pre-v0.2.0 (arrow2-era format)v0.2.0 or laterWipe the data directory. The Parquet encoding changed; old blocks cannot be read.
# Only for the arrow2-era boundary. This DESTROYS all stored telemetry.
# Export or archive anything you need first.
docker run --rm -v parqtel_data:/data alpine sh -c 'rm -rf /data/*'

Before wiping, confirm you are actually on the old format by checking whether /ready and /api/v1/stats report any existing blocks after an upgrade attempt.

Rollback#

Rolling back is safe within the current on-disk format: blocks are self-describing Parquet, and the previous binary reads them.

docker stop parqtel && docker rm parqtel
docker run -d --name parqtel \
  -p 8080:8080 -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:<previous-version>
↗

Roll back the configuration too if you changed it. A newer version may have introduced keys the older binary does not recognise. Startup validation reports all configuration errors together, so a rejected key is visible immediately in the logs.

Troubleshooting#

SymptomCauseResolution
/ready returns 503 after restoreData directory missing, wrong path, or wrong permissions.Check the mount path and that the container user (UID 65532) can read it.
Blocks visible in the directory but not in queriesIndex is stale and reconciliation has not run yet.Check startup logs for reconciled; restart if reconciliation did not complete.
Data missing after upgradeYou crossed the arrow2-era boundary without wiping.Back up, wipe the data directory, and re-ingest.
Pod restart-loops immediately after upgradeStartup probe budget exceeded by write-ahead log replay.Raise startupProbe.failureThreshold.
Older binary refuses to start after rollbackConfiguration contains keys the older version does not know.Restore the previous configuration file alongside the binary.
Backup is unexpectedly largeThe block index grows without retention bounding it (~23% of data volume).Expected. Exclude index.json from backups if size matters — it regenerates.
Restore appears to succeed but is emptyThe backup captured an empty or wrong volume.Verify the backup contains .parquet files before restoring.
