Troubleshooting#

Parqtel's known limitations, the operational problems they cause, and how to work around each one. This page also covers memory sizing and profiling, since the two largest operational risks in a Parqtel deployment are memory growth and slow flushes.

Read the Known limitations section before deploying.

Diagnostic first steps#

When something looks wrong, run these four commands before anything else:

# 1. Is the process alive?
curl -sf http://localhost:8080/health

# 2. Is storage usable? (503 = broken)
curl -sf http://localhost:8080/ready

# 3. What is stored, and is it growing?
curl -s http://localhost:8080/api/v1/stats | jq

# 4. Are flushes and WAL healthy?
curl -s http://localhost:8080/metrics | grep -E 'buffer_points|flush|wal|index_sidecar'

Known limitations#

These are documented behaviours, not bugs. Each has a workaround.

The in-memory buffer is unbounded#

Impact: Memory grows with buffered points. If ingest rate exceeds the flush rate for long enough, the process is killed by the OOM killer.

Why: Recent data must be queryable before it is flushed, and Parqtel does not reject ingest when the buffer grows.

Workaround: Size memory from the sizing formula rather than using a default, and alert on parqtel_buffer_points before the limit is reached. A monotonically rising buffer across a flush means flushes are failing.

No authentication or authorization#

Impact: Every endpoint — ingestion, queries, the console, and the OTLP gRPC port — is open. CORS allows any origin. Anyone who can reach the port has full access.

Why: Authentication is not implemented yet.

Workaround: Never expose ports 8080 or 4317 publicly. Terminate TLS and authenticate at a reverse proxy or service mesh. The optional profiling endpoints are disabled by default for this reason — keep them that way unless needed.

A range query does not evaluate its final partial step#

Impact: A range query returns one fewer sample at the trailing edge than you might expect.

Why: Prometheus-compatible step semantics: only complete steps are evaluated.

Workaround: Extend end by one step. This is the same behaviour Prometheus exhibits, so existing dashboards already account for it.

Instant queries only see the last 5 minutes#

Impact: A data point older than the lookback window is invisible to an instant query, even though it is stored and queryable.

Why: query.lookback_delta_ns defaults to 300000000000 (5 minutes), matching the Prometheus default. Alert evaluation uses the same window.

Workaround: Use /api/v1/query_range with an explicit window for historical data. To change the default, raise query.lookback_delta_ns.

Log and trace scans decode every column#

Impact: Log and trace search is slower than metric queries on large data sets.

Why: Column projection is implemented for metrics (7 of 15 columns) but not for logs or traces.

Workaround: Narrow the time range and filter aggressively. Log-to-metric pipelines would reduce volume, but they are not executed in v0.3.1 (see Log-to-metric pipelines); downsample at the Collector instead.

Traces are not compacted#

Impact: Trace files accumulate until retention deletes them, increasing file count and scan fan-out.

Why: The shipped server starts compaction for metrics and logs only. Traces receive retention and index persistence, but not compaction.

Workaround: Shorten trace retention if file count becomes a problem, or rely on the default 7-day retention to bound accumulation.

Alert rules only evaluate raw samples#

Impact: rate(), increase(), aggregations, and histogram_quantile() are parsed but not applied by the alert loop. Ratios and rates cannot be alerted on directly, and composed queries such as sum(rate(...)) can silently match no series.

Why: The alert loop builds its query plan without a step and thresholds the newest raw sample of each matching series.

Workaround: Alert on a gauge whose current value is the signal you care about, or precompute rates and ratios before ingestion (for example in an OpenTelemetry Collector processor). Recording rules are the intended in-product workaround, but they are stored and not executed in v0.3.1.

Background flushing requires the write-ahead log#

Impact: With ingest.wal_enabled = false, the background flush worker refuses to start and flushing becomes synchronous, so ingest latency includes the Parquet encode.

Why: Acknowledging a write before it is durable requires a log to acknowledge into.

Workaround: Leave ingest.wal_enabled = true (the default). If you disable it deliberately, expect higher ingest latency and a larger crash-loss window.

Silent truncation of query results#

Impact: Exceeding query.max_series (1000) or query.max_samples_per_series (10,000) returns no error — just fewer results.

Why: Limits are applied by truncation rather than rejection, for Prometheus compatibility.

Workaround: Compare totalSeriesCount in the response against the number of series actually returned. Aggregate to reduce series count, or raise the limits.

The block index grows without retention bounding it#

Impact: index.json was measured at ~23% of the data volume it describes and grows roughly 0.3 GB/day on a busy instance. Unlike blocks, it is not deleted by retention.

Why: The index stores per-block metadata, including label-value dictionaries for autocomplete.

Workaround: Monitor parqtel_index_sidecar_bytes and include the index in capacity planning. It regenerates from block footers if deleted, so it can be excluded from backups to save space.

Memory sizing#

Memory scales with buffered points, and the buffer is unbounded — so this is the single most important sizing decision you will make.

The model#

rss_peak ≈ BASELINE + (KiB_PER_POINT × peak_buffered_points) + FLUSH_TRANSIENT

BASELINE           ≈ 1.15 GiB   runtime, query engine, block index, allocator slack
KiB_PER_POINT      ≈ 6.3 KiB    measured slope between two load configurations
FLUSH_TRANSIENT    ≈ 80–140 MiB record batches + Parquet encode of one block

peak_buffered_points = ingest_rate_pts_per_sec × block_duration_secs

The sizing formula#

peak_buffer  = R × D              (ingest rate × block duration)
buffer_mem   = peak_buffer × 6.3 KiB
rss_peak     = 1.15 GiB + buffer_mem + 0.15 GiB
memory_limit ≥ 1.5 × rss_peak     (OOM safety factor)

Worked examples#

Ingest rateBlock durationPeak bufferEstimated rss_peakRecommended limit
0.5k pts/s120 s60k1.7 GiB2.5 GiB
1k pts/s120 s120k2.0 GiB3 GiB
2k pts/s120 s240k2.8 GiB4.5 GiB
1k pts/s300 s300k3.3 GiB5 GiB
5k pts/s60 s300k3.3 GiB5 GiB
↗

Rule of thumb: every extra 1k pts/s of ingest costs about 6.3 MiB of RAM per second of block duration. Adding 60 seconds to the block duration at 1k pts/s costs roughly 380 MiB. Logs are roughly 10× cheaper per record (strings arrive pre-owned, one record = one row). Traces cost about 2× a metric point.

Required allocator settings#

Ship these in every non-development deployment:

extraEnv:
  - name: MALLOC_ARENA_MAX
    value: "2"
  - name: MALLOC_TRIM_THRESHOLD_
    value: "134217728"     # 128 MiB

Measured effect: resident memory floor dropped from 2309 MiB to 1174 MiB, and memory is returned after each flush instead of pinning at the high-water mark.

Without the trim threshold, the allocator holds freed arena memory indefinitely, which turns the buffer behaviour into a ratchet rather than a sawtooth. This is the single largest source of "Parqtel ate 2.5 GiB and never gave it back" reports. The Helm chart sets the arena maximum by default.

↗

A musl or jemalloc/mimalloc build changes these constants. Re-measure if the base image changes.

OOM-avoidance rules#

  1. Size from the formula, verify with metrics. After deploying, watch parqtel_process_rss_bytes across at least three flush cycles. The flush peak must stay at or below 65% of the limit.
  2. Never raise the block duration to fix query latency. The 5-minute instant query lookback reads the buffer anyway; block duration only controls flush granularity.
  3. Alert before the OOM kill: ``promql parqtel_process_rss_bytes / on() kube_pod_container_resource_limits{resource="memory"} > 0.65 ``
  1. Buffer occupancy is the leading indicator. parqtel_buffer_points rising monotonically across a flush means the flush is failing (disk full? PVC stuck?) and an OOM is minutes away.
  2. CPU follows memory. A pod near its CPU limit with heavy encode work is about to stall flushes. Keep the CPU request at ≥ 0.5 core per 1k pts/s.

Profiling playbook#

Profiling is gated by telemetry.profiling_enabled (default false; endpoints return 404 while disabled) and is serialized by a process-wide lock — a second capture while one runs returns 429. Restrict the endpoints with a NetworkPolicy.

# 1. Forward the profiling port
kubectl -n monitoring port-forward deploy/parqtel 19092:9090 &

# 2. Memory decomposition: buffer vs RSS vs high-water mark
curl -s localhost:19092/debug/pprof/memory | jq

# 3. CPU hot spots — top frames over a window
curl -s 'localhost:19092/debug/pprof/summary?seconds=15&top=10' | jq

# 4. Full profile with an interactive flamegraph
go tool pprof -http=:0 'http://localhost:19092/debug/pprof/profile?seconds=30'
SettingDefaultNotes
telemetry.profiling_enabledfalseEndpoints return 404 while disabled.
telemetry.profiling_frequency99Sampling frequency in Hz (1–1000).

Use the memory decomposition first when investigating growth: it distinguishes a legitimately large live buffer from a resident-memory ratchet caused by allocator settings.
