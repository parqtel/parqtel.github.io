Quickstart#

Get Parqtel running, send a metric, a log, and a trace, and query all three back — in about five minutes.

This guide uses curl so you can copy and paste each step. In production you would point an OpenTelemetry SDK or Collector at Parqtel instead; that is covered in Ingest Telemetry.

Prerequisites#

  • Docker Engine 20.10 or newer, or Homebrew on Linux/macOS, or Rust 1.87+ to build from source.
  • Ports 8080 (HTTP API and console) and 4317 (OTLP gRPC) free on your machine.
  • curl available in your shell.

Everything below assumes localhost. Replace it with your host name if Parqtel runs elsewhere.

Step 1 — Install and start#

Docker (recommended)#

docker run -d \
  --name parqtel \
  -p 8080:8080 \
  -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:0.3.1

Homebrew (Linux & macOS)#

brew tap parqtel/tap
brew install parqtel-oss
parqtel serve

The Homebrew formula installs a prebuilt release binary, so no Rust toolchain is required.

From source#

git clone https://github.com/parqtel/parqtel-oss.git
cd parqtel-oss
cargo build --release
./target/release/parqtel serve

Step 2 — Verify it is up#

curl http://localhost:8080/health
# {"status":"ok"}

curl http://localhost:8080/ready
# {"status":"ready"}

These two endpoints are not interchangeable:

EndpointMeaningUse it for
/healthStatic liveness check. Always succeeds while the process runs.Container liveness probes.
/readyReads storage metadata and returns 503 if the data directory is unusable.Kubernetes readiness probes and load-balancer health checks.

Step 3 — Install verification checklist#

Before moving on, confirm all four:

  • [ ] curl http://localhost:8080/health returns {"status":"ok"}
  • [ ] curl http://localhost:8080/ready returns {"status":"ready"}
  • [ ] The console loads at <http://localhost:8080/ui>
  • [ ] The OTLP gRPC port 4317 is reachable (skip if you disabled gRPC)

Step 4 — Send your first metric#

Parqtel accepts metrics and logs over HTTP as protobuf or JSON; traces over HTTP are JSON-only (POST /v1/traces and /v1/traces/json). This example posts a single counter data point:

curl -X POST http://localhost:8080/v1/metrics/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceMetrics": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeMetrics": [{
      "metrics": [{
        "name": "http_requests_total",
        "sum": {"isMonotonic": true, "dataPoints": [{
          "asDouble": 1,
          "timeUnixNano": "'$(date +%s%N)'",
          "attributes": [
            {"key": "method", "value": {"stringValue": "GET"}},
            {"key": "status", "value": {"stringValue": "200"}}]}]}}]}]}]}'
↗

OTLP/JSON attribute format. In OTLP/JSON, attributes must be an array of {"key": …, "value": {"stringValue": …}} objects. A plain JSON object map is rejected. This follows the official OTLP JSON mapping and applies to metrics, logs, and traces alike.

Step 5 — Query the metric back#

curl "http://localhost:8080/api/v1/query?query=http_requests_total"

The response is a standard Prometheus vector:

{"status":"success","data":{"resultType":"vector","result":[ ... ]}}
↗

Why the point might not appear yet. An instant query only looks back 5 minutes (the Prometheus default, configurable via query.lookback_delta_ns). A point timestamped outside that window is not returned by an instant query — query it with a range query instead. This is a deliberate compatibility choice, not a bug; see Query Reference.

Step 6 — Send a log#

curl -X POST http://localhost:8080/v1/logs/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceLogs": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeLogs": [{"logRecords": [{
      "timeUnixNano": "'$(date +%s%N)'",
      "severityText": "INFO",
      "body": {"stringValue": "User logged in successfully"},
      "attributes": [{"key": "user_id", "value": {"stringValue": "user_123"}}]}]}]}]}'

Search for it (query is required; start/end are Unix seconds — pass a window explicitly):

curl "http://localhost:8080/api/v1/logs?query=severity%3E%3DINFO&start=$(date -d '-1 hour' +%s)&end=$(date +%s)"

Step 7 — Send a trace#

curl -X POST http://localhost:8080/v1/traces/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceSpans": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeSpans": [{"spans": [{
      "traceId": "5b8efff798038103d269b633813fc60c",
      "spanId": "eee19b7ec3c1b174",
      "name": "GET /checkout",
      "kind": 2,
      "startTimeUnixNano": "'$(date +%s%N)'",
      "endTimeUnixNano": "'$(($(date +%s%N) + 42000000))'",
      "status": {"code": 1}}]}]}]}'

Sending a span has a useful side effect: Parqtel automatically derives RED metrics — request, error, and duration samples, one per server-kind span — from the trace stream. Query them without any extra instrumentation:

curl "http://localhost:8080/api/v1/query?query=traces_service_requests_total"

Search traces directly (q is the ParqtelQL filter; start/end/limit are optional):

curl "http://localhost:8080/v1/traces/search?q=service.name%3D%22my-web-app%22&limit=20"

Step 8 — Correlate across signals#

/v1/correlate takes an anchor (signal, timestamp, and a JSON label set) and returns records from another signal inside a time window. A trace_id anchor is the strongest correlation dimension:

curl -G "http://localhost:8080/v1/correlate" \
  --data-urlencode "anchor_signal=traces" \
  --data-urlencode "anchor_timestamp_ns=$(date +%s%N)" \
  --data-urlencode 'anchor_labels={"trace_id":"5b8efff798038103d269b633813fc60c"}' \
  --data-urlencode "target_signal=log" \
  --data-urlencode "window_ns=60000000000" \
  --data-urlencode "limit=50"

target_signal is log or metric (singular). window_ns defaults to 5 s and limit to 50.

Step 9 — Open the console#

Browse to <http://localhost:8080/ui>. The console ships inside the same binary and needs no separate install. It includes:

  • An overview dashboard with live ingestion rates
  • A PromQL query builder
  • Log browsing with facets
  • Trace browsing grouped by trace, with a waterfall view
  • An alert stream

See Visualise Telemetry for a guided tour.

Step 10 — Confirm durability#

Parqtel acknowledges a write once it reaches the write-ahead log, not once the Parquet block is on disk. Crash loss is therefore bounded by ingest.wal_sync_interval_ms (default 1 second) rather than a whole block window, and anything still in the log is replayed on startup.

# Storage summary: blocks, rows, disk bytes, index size per signal
curl -s localhost:8080/api/v1/stats | jq

# Flush and WAL activity
curl -s localhost:8080/metrics | grep parqtel_flush

Read Durability & Recovery for the commit sequence and tuning, and Storage Model for how blocks are laid out.

Troubleshooting#

SymptomLikely causeResolution
curl cannot connect on :8080Port not published, or the container exited.Check docker ps; confirm -p 8080:8080 was passed. Read logs with docker logs parqtel.
/ready returns 503The data directory is missing or not writable.Confirm the volume mount (for Docker, -v parqtel_data:/data) and that the path is writable by the container user.
Metric was accepted but the query returns nothingThe data point's timestamp falls outside the 5-minute instant-query lookback.Use /api/v1/query_range with a window that covers the timestamp, or resend with a current timestamp.
400 Bad Request on an OTLP/JSON postattributes was sent as a JSON object instead of an array.Use the [{"key": …, "value": {"stringValue": …}}] form shown in Step 4.
Query returns fewer samples than expectedPrometheus compatibility behaviour: a range query does not evaluate its final partial step.Extend end by one step. See Query Reference.
Port 9090 does not respondYou followed the Docker Compose instructions, which publish Parqtel on :9090.Use :9090 with Compose, or :8080 for a plain docker run.
