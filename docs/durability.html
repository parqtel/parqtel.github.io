Durability & Recovery

Parqtel acknowledges a write once the row is in the write-ahead log, not once the Parquet block is on disk. This page documents what that guarantee is, how the commit ordering makes it safe at every crash point, and how to bound or widen it.

↗

Implemented in parqtel-core/src/wal.rs (~880 lines), wired into ingest in parqtel-ingest/src/service.rs and bootstrapped in parqtel-server/src/main.rs.

The problem it solves

A Parquet block is only durable once its file has been written and renamed. Everything accepted into the in-memory buffer since the last flush is lost on a crash — and with a duration-based block window, that window is measured in hours (2 h for metrics by default). For an observability store whose entire purpose is to hold the data you want during an incident, that is the wrong trade.

The write-ahead log narrows the exposure from the block window to the fsync interval: 1 second by default.

On-disk format

One WAL directory per signal, under <data_dir>/wal/<signal>/:

data/
├── wal/
│   ├── metrics/   00000000000000000000.wal  …  commit
│   ├── traces/    00000000000000000000.wal  …  commit
│   └── logs/      00000000000000000000.wal  …  commit
├── index.json
├── *.parquet
├── logs/
└── traces/

Record framing

┌──────────────┬──────────────┬───────────────────────────┐
│ u32 LE length│ u32 LE CRC32 │ payload (JSON, `len` B) │
│   4 bytes     │   4 bytes    │                           │
└──────────────┴──────────────┴───────────────────────────┘
        RECORD_HEADER_LEN = 8 bytes
  • One record per decoded signal value. Each Metric, LogRecord and Span becomes one JSON record, appended under the rotator lock. The record type is not tagged in the framing — it is a property of the signal directory, supplied by the caller's generic parameter.
  • CRC32 over the payload detects a torn tail from a crash mid-append.
  • Segments are named %020d.wal — zero-padded to 20 digits so they sort lexically in sequence order.
  • The commit file is a plain decimal u64, written commit.tmp → rename.
⚠

What "durable" means here. Throughout this subsystem, durability means renamed into place. The Parquet block, the commit file and index.json are all written tmp-then-rename with no explicit fsync and no directory fsync. Only the WAL segment bytes get an fsync/fdatasync. On a machine loss you may therefore lose a recently written block or commit point even though the WAL itself is intact — the WAL bounds the loss window, it does not make the filesystem a transactional store.

Every append also flushes the 64 KiB BufWriter into the page cache (write(2)), without which a process kill would lose everything still buffered — exactly the case the WAL exists for. A segment must stay under 4 GiB, since the segment sequence occupies the high 32 bits of the position.

Positions

A position is (segment_sequence << 32) | (byte_offset + 1). Two properties fall out of this:

  • It is monotonic across segments and comparable without opening any file.
  • It is 1-based — the first record of the first segment is position 1, not 0. WalPosition::START is 0 and means "nothing committed"; a 0-based position would make the very first record look already-committed and silently drop it on replay.

The commit protocol

A block flush and the WAL must agree, or a crash either duplicates data or loses it. The sequence is:

  1. Append and acknowledge

    Rows are appended to the WAL, then the HTTP request is acknowledged. append() returns the position that covers the record.

  2. Snapshot on flush

    A flush takes rows, snapshotting the WAL position it is about to cover (covered). The snapshot is taken under the rotator lock, which is also held for the append — so WAL order and writer order are the same total order, and the committed position is provably correct.

  3. Write and rename the block

    The Parquet encode runs on spawn_blocking; the file is written to a temporary name and renamed into place, which is what makes a block atomic.

  4. Publish, then wait for the sidecar

    BlockMetadata goes to the index task over an unbounded channel, and the flush blocks on a tracked durability handle until the index.json sidecar has been written and fsynced.

  5. Commit, then delete

    Only then is the commit point advanced to covered. Segments entirely below the commit are deleted.

The commit file is the single source of truth, and it is advanced after the rename, so every crash point is safe. Segments with seq < commit.segment() are then deleted — never the segment currently being appended to, which is why the on-disk working set stays bounded at roughly one segment plus whatever is uncommitted.

Crash afterResult
(1) appendReplayed. Nothing on disk yet — correct.
(2) snapshotReplayed. No block written — correct.
(3) rename, before (4)The block exists but is not committed, so it is not in the index. The WAL still holds the rows and replay writes them again. The orphan is invisible, so there is exactly one copy.
(4) commit, before (5)Rows are covered. Replay skips everything at or below the commit, so the leftover segments are discarded rather than duplicated.
⚠

Advancing the commit before the rename could lose a block — the one failure a WAL exists to prevent. This ordering is the design.

Failing safe

Step 4 is bounded by INDEX_DURABILITY_TIMEOUT. A wedged index task must not stall ingest indefinitely, and committing while the index is behind is exactly the window this handshake closes. On timeout — or if the index task is dropped — Parqtel does not commit:

ERROR timed out waiting for the block index to become durable;
      leaving the WAL uncommitted so the rows are replayed

WARN  index task dropped before the sidecar was persisted;
      leaving the WAL uncommitted so the rows are replayed

The cost is a duplicate row after restart, which the index reconciliation and the commit-point skip collapse; the alternative would be data loss.

Buffer draining

The in-memory buffer is drained by the rotator when a block becomes durable, never when a flush is merely scheduled. Draining early would leave rows in neither the buffer nor any block — invisible to every query until the encode landed.

Replay and recovery

At startup, for each signal, Parqtel reads the commit point and replays everything above it. replay() walks segments in order and hands each record to a callback, tracking four counters:

CounterMeaning
recordsRecords handed to the caller.
skippedRecords at or below the commit point (already covered), plus any that fail to deserialise.
truncated_bytesBytes discarded from the tail of a segment — what a crash mid-append leaves behind.
segments_removedSegments deleted after a successful replay.

Torn tails

The reader stops at the first record that is truncated or fails its CRC, then set_lens the segment to that boundary and fsyncs, so the next append starts from a clean edge:

WARN  WAL had a torn tail from a crash; the unusable bytes were dropped
      signal=metrics bytes=142
INFO  WAL replay complete
      signal=metrics records=312 skipped=0 truncated_bytes=0 elapsed=41ms

A record that frames correctly but fails to deserialise is not a stop condition — stopping there would silently drop every later record — so it is logged and skipped:

WARN  skipping undecodable WAL record  position=2:14 error=…
ℹ

truncated_bytes is usually 0 after a real crash. Writers are opened before replay runs, and opening walks the length fields and rewinds the segment to the last intact boundary — which silently discards a torn tail before the counter can see it. Only a CRC failure, which that rewind does not check, reaches the replay truncation path. The counter is therefore a weak signal; the presence of a block replayed at all is the reliable one.

A CRC mismatch breaks the rest of that segment, because record offsets cannot be re-synchronised. Later segments are still read — a single corrupt segment costs at most a segment.

Idempotency

Replay is not a repair operation — it is a re-ingest. Recovered records are pushed back through the same public entry points live exporters use (ingest_metrics / ingest_logs / ingest_spans, which are pub for exactly this reason), so recovery cannot diverge from the normal path. They land in a fresh block and produce a new covered position.

Two consequences worth knowing:

  • Recovered records are re-appended to the WAL. Writers are opened before replay, so each recovered row exists twice — at its old position and its new one — until the next commit covers the second. That transiently doubles WAL bytes for the replayed window; it is self-cleaning.
  • Replayed traces run through tail sampling and the RED bridge again. Sampling is a deterministic trace_id hash, so the decision is identical and derived metrics are not double-counted in effect — but a 3-span replay does re-derive its traces_service_* metrics.

The commit-point skip is what prevents the duplicate case: a segment whose records are all below the commit is discarded whole rather than replayed.

Startup ordering

Replay runs before the listener binds, so a recovering instance never accepts traffic on a half-restored dataset. The sequence is: create data directories → load and reconcile each index → open the WALs (failure aborts startup) → build services → start the flush worker → replay → build state and router → bind.

On shutdown, tasks are aborted, then the rotator is flushed and the flush worker stopped — the worker sender is dropped and its handle awaited, so every in-flight encode finishes. A graceful shutdown cannot leave a block half-written or skip a WAL commit.

Startup cost

Replay is proportional to unflushed WAL — so it is slow exactly when the pod is least healthy. That is why the Helm chart exposes startupProbe: the hardcoded budget was 150 s, an install returning with a large WAL replay exceeds it, gets killed mid-replay, and restarts with an even larger WAL. See probes.

Self-healing block index

Reconciled at startup, in both directions, then persisted if anything changed:

  • Adopt — block files the index has never seen are recovered from their Parquet footer and added.
  • Drop — index entries whose file has gone are removed.

When anything was repaired you get one warning per signal:

WARN  block index did not match the data directory; reconciled from the
      block files. Metric names may be a range until the block is rewritten
      by compaction, and recovered blocks have no label dictionary until then.
      signal=traces adopted=3 dropped=1 unreadable=0
⚠

A recovered block carries an empty metric-name set, which means "unknown" — not "matches nothing". It stays visible to every query, but name-based pruning does not apply to it until compaction rewrites it with a full flush-time index, and label-value autocomplete stays empty until then.

Signal detection reads the schema, not the filename (severity_text → Logs, then metric_kind → Metrics, then start_time_ns → Traces — the order matters because log blocks also carry a span_id column). A wrong filename can only cause a block to be missed, never wrongly adopted.

⚠

Trace reconciliation cannot adopt its own blocks. Trace blocks are written to the parent data/ directory while the trace sidecar lives in data/traces/, so reconciliation scans a directory that does not hold them. A lost trace index is rebuilt from the WAL replay and the normal flush path, not by adoption.

In the normal case this is one read_dir and the sidecar is only rewritten when something actually changed.

Metrics and traces share one switch — they live under the same data directory. Disabling the WAL emits an explicit warning per signal at startup:

WARN  WAL is disabled for this signal; a crash can lose up to a whole block window
↗

A WAL that cannot be opened fails startup. Continuing would mean accepting data we cannot promise to recover, which is exactly the guarantee the WAL exists to provide.

Tuning

KeyTypeDefaultEffect
ingest.wal_enabledBooleantrueWAL for metrics and traces. Also gates the background flush worker — see below.
ingest.log_wal_enabledBooleantrueWAL for logs.
ingest.wal_sync_modeStringintervalnone (write only — survives a process crash, not machine loss) · interval (periodic fsync) · always (fsync per record). Not none by default: a default that quietly means "do not sync" is a footgun in a durability feature.
ingest.wal_sync_interval_msInteger1000How often the WAL is fsynced in interval mode. This is your crash-loss bound. Clamped to a 1 ms floor, so 0 means 1 ms, not "never".
ingest.wal_max_segment_bytesInteger67108864 (64 MiB)Size at which the WAL rolls to a new segment. A segment is deleted once the commit passes it, so the on-disk working set stays bounded at roughly one segment plus whatever is uncommitted. A restart reuses the newest segment unless it is already full.
ingest.max_inflight_flushesInteger4Max block encodes in flight, which also bounds the flush queue. Requires the WAL.
ingest.rotator_shardsInteger4Metrics writer shards (1–256). The WAL append happens under the shard lock, so WAL order and writer order are the same total order — the property that makes the committed position provably correct. Shards merge into one block, so block count, query fan-out and durability are unchanged.
server.index_persist_interval_secsInteger2Sidecar debounce. A flush now forces the write rather than waiting for this interval.

These are flat fields — there is no nested [ingest.wal] table. The Helm chart renders wal_enabled, log_wal_enabled, wal_max_segment_bytes and wal_sync_interval_ms; it does not render wal_sync_mode or max_inflight_flushes. Note the chart default walMaxSegmentBytes: 16777216 (16 MiB) overrides the binary's 64 MiB default.

# fsync every 200 ms instead of 1 s — smaller loss window, more IO
export PARQTEL__INGEST__WAL_SYNC_INTERVAL_MS=200
export PARQTEL__INGEST__WAL_SYNC_MODE=always      # fsync per record; strongest guarantee

# 16 MiB segments: lower peak disk, more segment churn
export PARQTEL__INGEST__WAL_MAX_SEGMENT_BYTES=16777216

The background flush worker requires a WAL

A request that crosses the block cap is acknowledged once the WAL holds its rows rather than after the ~125 ms Parquet encode — on a realistic 7 MiB batch the encode is about 125 ms of a ~300 ms request, and it serialises concurrent requests behind the flush lock.

That is only sound with a WAL: without one, an acknowledged-but-unwritten flush is unrecoverable. So with wal_enabled = false the worker refuses to start and metrics flushing falls back to synchronous:

WARN  metrics WAL is disabled; flushing synchronously so a request is never
      acknowledged before its data is recoverable

Degrading to the safe behaviour beats silently weakening durability. wal_enabled = false remains a legitimate operator choice — just not one that can also have a background flush. Logs and traces always flush inline, with or without a WAL.

Observing durability

There is no WAL HTTP endpoint, admin command or CLI flag. Replay outcomes surface in the startup log, and durability pressure shows up through the flush and index metrics:

INFO  WAL replay complete  signal=metrics records=312 skipped=0 truncated_bytes=0 elapsed_ms=41
INFO  WAL replay complete  signal=logs   records=0   skipped=0 truncated_bytes=0 elapsed_ms=0
INFO  WAL replay complete  signal=traces records=18   skipped=0 truncated_bytes=0 elapsed_ms=6

curl -s localhost:8080/metrics | grep -E 'parqtel_(index|flush|ingest_lock)'
MetricRead it for
parqtel_index_sidecar_bytes{signal}Index size on disk — measured, not assumed. See storage.
parqtel_index_pending_writes{signal}Mutations queued for the next sidecar write — what the commit handshake is waiting behind.
parqtel_index_lock_wait_secondsTime writers spend waiting on the index lock.
parqtel_flush_duration_seconds, parqtel_flush_inflight, parqtel_flush_rows_totalEncode cost, worker saturation, block sizes.
parqtel_ingest_lock_wait_seconds, parqtel_ingest_rotator_shardsThe WAL append happens under the shard lock, so this is where WAL write cost shows up — measured at ~54 ns mean over 9 695 acquisitions for metrics (126 ns logs, 1.2 µs traces). Raise rotator_shards only if this grows.

Replays across metrics, logs and traces are verified against SIGKILL-ed containers in the test suite — acknowledged points survive a crash without a graceful shutdown — so this is a tested contract rather than an aspiration.

Upgrading across versions

Rolling back is safe. Blocks are self-describing Parquet and the previous binary reads them.

Rolling forward may not be. The arrow2 → arrow 59 migration changed the on-disk encoding: Parquet blocks written by arrow2-era builds are unreadable by the current reader. When upgrading across that boundary, wipe the data directory.
