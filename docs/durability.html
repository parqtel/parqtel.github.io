Internals

Durability & Recovery#

Parqtel acknowledges a write once the row is in the write-ahead log, not once the Parquet block is on disk. This page explains exactly what that guarantee covers, which settings widen or narrow it, and what happens between a crash and the first query served.

Read it before you decide ingest.wal_enabled is optional. The default protects you; turning it off changes the loss window from one second to two hours for metrics.

Why the WAL exists#

A Parquet block is durable only once the file has been written and renamed into place. Everything accepted into the in-memory buffer since the last flush would be lost on a crash — and with a duration-based block window, that window is measured in hours (2 h for metrics by default). For a store whose purpose is to hold the data you need during an incident, that is the wrong trade.

The write-ahead log narrows the exposure from the block window to the fsync interval: 1 second by default.

What "durable" means here#

The single most important thing to internalise:

↗

In Parqtel, "durable" means renamed into place. The Parquet block, the commit file, and the index sidecar are all written to a temporary name and renamed, with no explicit fsync and no directory fsync. Only the WAL segment bytes get an fsync/fdatasync.

The practical consequences:

EventWhat survives
Process crash (the process is killed)Everything up to the last acknowledged append. Appends are flushed out of the in-process buffer to the operating system immediately, so a killed process loses nothing acknowledged.
Machine loss (power cut, host failure)Everything except up to one sync interval in interval mode. A recently written block or commit point may be lost even though the WAL itself is intact.
wal_sync_mode = "none"The WAL is written but never explicitly synced: a process crash is survivable, a machine loss is not.
wal_sync_mode = "always"An fsync per record. This is the strongest guarantee and it costs throughput.
wal_enabled = falseNo protection at all — a crash loses a whole block window.

The WAL bounds the loss window; it does not turn the filesystem into a transactional store.

The commit protocol#

A block flush and the WAL must agree. If they disagree, a crash either duplicates data or loses it. Parqtel orders the work so that every crash point is safe.

Why the order matters#

Crash pointResultCorrect because
(1) After the appendThe row is replayed from the WAL.Nothing on disk yet.
(2) After the snapshotThe row is replayed from the WAL.No block was written.
(3) After the rename, before (4)The block exists but is not committed and is not in the index. The WAL still holds the rows, so replay writes them again. The orphan block is invisible.There is exactly one copy.
(4) After the commit, before (5)Replay skips everything at or below the commit, so the leftover segments are discarded rather than duplicated.Rows are covered.
↗

Advancing the commit before the rename would lose a block — the one failure a WAL exists to prevent. The ordering above is the design, not an implementation detail.

Failing safe#

Step 4 is bounded by a timeout. A wedged index task must not stall ingest indefinitely, and committing while the index is behind is exactly the window the handshake closes. On timeout — or if the index task is dropped — Parqtel does not commit, logs the condition, and leaves the rows in the WAL for replay.

The cost is a duplicate row after restart, which the commit-point skip and index reconciliation collapse. The alternative would be data loss.

Buffer draining#

The in-memory buffer is drained when a block becomes durable — never when a flush is merely scheduled. Draining early would leave rows in neither the buffer nor any block: invisible to every query until the encode landed.

On-disk working set#

There is one WAL directory per signal under the data directory:

SignalWAL locationGated byDefault
Metrics<storage.data_dir>/wal/metricsingest.wal_enabledtrue
Traces<storage.data_dir>/wal/tracesingest.wal_enabledtrue
Logs<logs.data_dir>/wal/logsingest.log_wal_enabledtrue

Metrics and traces share one switch because they share a data directory.

The WAL rolls to a new segment at ingest.wal_max_segment_bytes (default 67108864, 64 MiB). Segments entirely below the commit point are deleted — never the segment currently being appended to. The on-disk working set is therefore bounded at roughly one segment plus whatever is uncommitted, regardless of how long the server has been running or how much data you retain.

A restart reuses the newest segment unless it is already full.

Recovery at startup#

Replay runs before the server binds its listener, so a recovering instance never accepts traffic against a half-restored dataset.

A WAL that cannot be opened fails startup. Continuing would mean accepting data Parqtel cannot promise to recover — precisely the guarantee the WAL exists to provide.

What replay does#

Replay reads the commit point for each signal and re-applies everything above it. It reports four counters per signal at startup:

CounterMeaning
recordsRecords handed to the ingestion path.
skippedRecords at or below the commit point (already covered), plus any that fail to decode.
truncated_bytesBytes discarded from the tail of a segment — what a crash mid-append leaves behind.
segments_removedSegments deleted after a successful replay.

A representative startup log line:

INFO  WAL replay complete signal=metrics records=312 skipped=0 truncated_bytes=0 elapsed_ms=41
↗

truncated_bytes is usually 0 even after a real crash. The writer opens segments before replay and rewinds each to its last intact record boundary, so a torn tail is normally dropped before the counter can see it. Treat the presence of a replay at all as the reliable signal, not this counter.

Torn tails and corrupt records#

ConditionBehaviour
Truncated record at the tailThe reader stops there, truncates the segment to the last good boundary, and syncs, so the next append starts from a clean edge. A warning names the signal and the number of unusable bytes.
Checksum failureThe rest of that segment is abandoned, because record offsets cannot be re-synchronised. Later segments are still read, so a single corrupt segment costs at most one segment.
A record that frames correctly but cannot be decodedLogged and skipped, not a stop condition — stopping would silently drop every later record.

Replay is a re-ingest, not a repair#

Recovered records are pushed back through the same entry points live exporters use, so recovery cannot diverge from the normal path. They land in a fresh block and produce a new commit position. Two consequences are worth knowing:

  • Recovered records are re-appended to the WAL. Writers open before replay, so each recovered row exists twice — at its old position and its new one — until the next commit covers the second. This transiently doubles WAL bytes for the replayed window and is self-cleaning.
  • Replayed traces run through tail sampling and RED derivation again. Sampling is a deterministic hash of the trace ID, so the keep/drop decision is identical. RED derivation is not deduplicated, however: a replayed trace re-emits its traces_service_* samples at the original span timestamp, so a replay window can contain duplicate metric samples. Treat RED counts that span a crash boundary as approximate.

The commit-point skip is what prevents duplication: a segment whose records are all below the commit is discarded whole rather than replayed.

Startup cost#

Replay is proportional to unflushed WAL, so it is slow exactly when the pod is least healthy. If you run Kubernetes, give the startup probe a budget that can absorb a large replay. A pod killed mid-replay restarts with an even larger replay, which is a loop you want to avoid — raise the probe's failure threshold or period rather than deleting the probe. See Deploy.

Per-signal coverage and observability#

There is no WAL HTTP endpoint, admin command, or CLI flag. Durability surfaces through the startup log and through flush and index metrics.

MetricRead it for
parqtel_index_sidecar_bytes{signal}Index size on disk per signal.
parqtel_index_pending_writes{signal}Mutations queued for the next sidecar write — what the commit handshake is waiting behind.
parqtel_index_lock_wait_secondsTime writers spend waiting on the index lock.

docker logs parqtel 2>&1 | grep "WAL replay complete"

# Flush and index pressure
curl -s localhost:8080/metrics | grep -E 'parqtel_(index|flush|ingest_lock)'

Raise ingest.rotator_shards only if parqtel_ingest_lock_wait_seconds shows real contention — each shard costs one writer buffer.

Tuning durability#

KeyTypeDefaultEffect
ingest.wal_enabledBooleantrueWAL for metrics and traces. Also gates the background flush worker.
ingest.log_wal_enabledBooleantrueWAL for logs.
ingest.wal_sync_modeString"interval"none (write only — survives a process crash, not machine loss) · interval (periodic fsync) · always (fsync per record).
ingest.wal_sync_interval_msInteger1000How often the WAL is synced in interval mode. This is your crash-loss bound. Clamped to a 1 ms floor, so 0 means 1 ms, not "never".
ingest.wal_max_segment_bytesInteger67108864 (64 MiB)Size at which the WAL rolls to a new segment. A segment is deleted once the commit passes it.
ingest.max_inflight_flushesInteger4Maximum block encodes in flight; also bounds the flush queue. Requires ingest.wal_enabled.
ingest.rotator_shardsInteger4Metrics writer shards (1–256). Shards merge into one block, so block count, query fan-out, and durability are unchanged.
server.index_persist_interval_secsInteger2Sidecar debounce. A flush forces the write rather than waiting for this interval.

These are flat keys — there is no nested [ingest.wal] table.

Choosing a sync mode#

GoalSetting
Default balancewal_sync_mode = "interval", wal_sync_interval_ms = 1000
Smaller loss windowLower ingest.wal_sync_interval_ms (for example 200)
Strongest guaranteewal_sync_mode = "always"
Maximum throughput, accepts machine-loss exposurewal_sync_mode = "none"
# Sync every 200 ms instead of 1 s — smaller loss window, more I/O
export PARQTEL__INGEST__WAL_SYNC_INTERVAL_MS=200

# fsync per record — strongest guarantee
export PARQTEL__INGEST__WAL_SYNC_MODE=always

# Smaller segments: lower peak disk, more segment churn
export PARQTEL__INGEST__WAL_MAX_SEGMENT_BYTES=16777216
↗

A default that quietly means "do not sync" would be a footgun in a durability feature, which is why interval and not none is the default.

Why the background flush worker needs the WAL#

A request that crosses the row cap is acknowledged once the WAL holds its rows, rather than after the Parquet encode — a large encode is a meaningful fraction of the request, and it serialises concurrent requests behind the flush lock. That is only sound when the rows are already logged: without a WAL, an acknowledged-but-unwritten flush would be unrecoverable.

With ingest.wal_enabled = false the worker refuses to start and metrics flushing falls back to synchronous. The server logs a warning naming the signal. Degrading to the safe behaviour beats silently weakening durability. wal_enabled = false remains a legitimate operator choice — just not one that can also have a background flush. Logs and traces always flush inline, with or without a WAL.

Disabling the WAL also emits an explicit warning per signal at startup, saying that a crash can lose up to a whole block window.
