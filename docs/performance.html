Performance & Scaling#

Parqtel trades sub-second writes for low resource usage and cheap long-term storage. This page gives you the measured numbers, the memory model behind them, and the settings that move each one — so you can size a deployment and predict where it will bend before it breaks.

Every figure below was measured against a running release build on a single machine. The ratios travel better than the absolute numbers — re-measure on your own hardware, storage, and cardinality before quoting them in a capacity plan.

How a request spends its time#

The design goal is that nothing on the left of that diagram touches disk on the slow path. The numbers below show where that succeeded and where the remaining cost sits.

Ingest#

MeasurementValue
Ingest p504.4 ms per batch
Ingest p9963 ms per batch
WAL append cost under the shard lock (metrics)~53 ns mean over 9 555 acquisitions
WAL append cost (logs / traces)126 ns / 1.2 µs
Decode and buffer push~550 K points/second
Flush to Parquet, 50 K points~830 K points/second (compression-bound)

The WAL append is the only durability work on the request path, and it is measured in nanoseconds. A request that crosses the row cap is acknowledged once the WAL holds its rows, with the encode handed to the background flush worker — which is why a large batch does not add the encode's ~125 ms to the request.

Backpressure degrades rather than queues. When the flush worker's queue is full, the encode happens inline. Ingest slows to the synchronous rate instead of growing an unbounded backlog you cannot see.

↗

Background flushing requires a WAL. With ingest.wal_enabled = false the worker does not start and every flush is synchronous. See Durability & Recovery.

Query#

ChangeWorkloadBeforeAfterΔ
Prepared log/trace queries20 000 rows1.000 s4.881 ms205×

What these mean in practice:

  • Log and trace search compiles its query once per request, not once per row. A prepared query moves regex compilation and case folding out of the row loop, with an allocation-free substring scan.
  • Query evaluation runs off the request-handling threads, so a wide range query cannot starve ingest. Single-query latency is unchanged — the gain is concurrency and p99 stability rather than a faster mean.
  • Series labels are shared, not copied per step. A 1 000-series × 1 000-step query previously produced roughly 20 million identical string allocations.
  • Steps stream into the response as they are produced, so peak memory is one step's vector rather than the whole result.

The one metric that stayed flat#

A full-range query over an already-fast scan did not get faster: executor-side grouping and downsampling dominate once scanning is cheap. Optimising the scan moves narrow queries, not wide ones. If a full-range query is your problem, the fix is query shape — a narrower window or an aggregation the engine can push down — not a faster disk.

Pruning#

Pruning is the reason a query does not read the whole dataset. Rows are written grouped by metric name, so a row group's name statistics are exact.

Statistics versus bloom filters#

The decisive measurement, on one block of 100 000 rows (200 metrics × 500 points), querying one metric of the 200:

ConfigurationBlock sizeWrite timeQuery time
Neither1.29 MB38 ms30.33 ms
Row-group statistics only1.47 MB55 ms2.34 ms
Statistics + bloom filter1.49 MB42 ms2.49 ms

12.1× faster queries for 14 % more bytes, from statistics alone. Adding bloom filters on top changes the query by nothing measurable and costs roughly 2 % more size — so bloom filters are kept only as a fallback for blocks whose statistics are absent or truncated.

A query for a metric that is not in the block costs 0.02 ms instead of 30 ms: the candidate set is empty before a reader is even built.

Service-level pruning#

Multi-tenant shape — one metric, eight services, one row group each, querying one service:

QueryTimeRows decoded
Without the service predicate2.05 ms4 000 (the whole block)
With service pruning0.43 ms500

4.8×, entirely from the service dimension — metric-only pruning cannot help there, because all eight row groups hold the same metric.

Column projection#

Query shapeNo projectionProjectedChange
Single metric of 200 (1 row group)2.47 ms2.33 ms−6 %
One service of 8 (1 row group)0.40 ms0.34 ms−15 %
Full-block scan, 100 000 rows53.10 ms38.13 ms−28 %

Projection pays in proportion to how many row groups a query must read: a typical query decodes one row group, so there is little left to skip. It is worth most on full-block scans. Log and trace scans are not projected at all — see Known limitations.

Label-value autocomplete#

The query builder must never enumerate a high-cardinality label. Worst case measured: 100 000 distinct values across 300 000 buffered points.

PathLatency (best of 20)Payload per keystroke
Bounded top-10, no prefix~1.2 µs10 values
Bounded top-10, prefix typed~1.2 µs10 values
Full enumeration (unbounded dropdown)~15.6 ms100 000 values

That is roughly 13 000× faster and 10 000× less data per keystroke. The flush-time per-field dictionary is capped at 10 000 values, so even cold lookups stay bounded, and GET /api/v1/label/{name}/values clamps limit to 100.

Memory sizing#

Memory is the dominant operational risk, and it is predictable. The in-memory buffer is what makes recent data immediately queryable, and it has no size limit — so its footprint is a function of how fast you ingest and how long a block window runs.

The formula#

peak_buffer   = ingest_rate_pts_per_sec × block_duration_secs
buffer_mem    = peak_buffer × 6.3 KiB
rss_peak      = 1.15 GiB + buffer_mem + 0.15 GiB
memory_limit  ≥ 1.5 × rss_peak
TermValueNotes
Baseline≈ 1.15 GiBRuntime, query engine, block index, allocator slack.
Per buffered point≈ 6.3 KiBUpper bound — it predates two changes that reduced per-point cost.
Flush transient80–140 MiBRecord batches plus the encode of one block.
Safety factor1.5×Applied to peak RSS.

Worked examples#

Ingest rateBlock durationPeak bufferEstimated peak RSSRecommended limit
0.5 k pts/s120 s60 k1.7 GiB2.5 GiB
1 k pts/s120 s120 k2.0 GiB3 GiB
2 k pts/s120 s240 k2.8 GiB4.5 GiB
1 k pts/s300 s300 k3.3 GiB5 GiB
5 k pts/s60 s300 k3.3 GiB5 GiB

Rules of thumb:

  • Every extra 1 k points/second costs about 6.3 MiB of RAM per second of block duration.
  • Adding 60 s to the block duration at 1 k pts/s costs roughly 380 MiB.
  • Logs are about 10× cheaper per record than metric points (strings arrive pre-owned, one record is one row).
  • Traces are about 2× a metric point.

Allocator settings you should ship#

These are validated on staging and belong in every non-development deployment:

extraEnv:
  - name: MALLOC_ARENA_MAX
    value: "2"
  - name: MALLOC_TRIM_THRESHOLD_
    value: "134217728"   # 128 MiB

Measured effect: RSS floor 2309 → 1174 MiB, and RSS returns after each flush instead of pinning at the high-water mark. Without the trim threshold, the allocator holds freed arena memory indefinitely and the buffer ratio above becomes a ratchet rather than a sawtooth — the single largest source of "Parqtel ate 2.5 GiB and never gave it back" reports. A different allocator or base image changes these constants; re-measure if you change the image.

Sizing rules#

RuleWhy
Size from the formula, then verify with the SLIs.Watch parqtel_process_rss_bytes across at least three flush cycles; the flush peak must stay ≤ 65 % of the limit.
Never raise the block duration to fix query latency.The 5-minute instant-query lookback reads the buffer anyway; block duration only controls flush granularity. Raising it is a memory decision, not a query decision.
Alert before the OOM kill.parqtel_process_rss_bytes / on() kube_pod_container_resource_limits{resource="memory"} > 0.65
Buffer occupancy is the leading indicator.parqtel_buffer_points rising monotonically across a flush means the flush is failing — disk full, or a stuck volume — and an OOM is minutes away.
CPU follows memory.Keep the CPU request at ≥ 0.5 core per 1 k points/second; a pod near its CPU limit with heavy encode work is about to stall flushes.

Scaling guidance#

DimensionGuidance
Vertical firstA single instance handles the throughput above. There is no cluster to size and no separate archive tier.
Block durationThe primary lever on memory. Halving it halves the buffer at the cost of more blocks and a larger index sidecar.
Block sizeLarger blocks mean fewer files, a smaller index.json, and less scan fan-out — but a longer flush and a bigger flush transient.
Row group sizeThe unit of pruning. Keep it well below max_rows_per_block; validation enforces the relationship for you.
Compaction budgetRaise storage.compaction_max_merges_per_pass if small blocks arrive faster than the default budget retires them.
Index growthRoughly 0.3 GB/day at ~32 blocks/minute, and it is not bounded by retention. Fewer, larger blocks means a smaller index.
ShardingA single instance is the unit of scale. Scale out by running independent instances per tenant or environment, not by adding nodes to one store.

Profiling#

Profiling is disabled by default and gated by telemetry.profiling_enabled. While disabled the endpoints return 404; captures are serialised by a process-wide lock, so a second capture while one runs returns 429.

EndpointPurpose
GET /debug/pprof/summary?seconds=15&top=10Hot frames over a window.
GET /debug/pprof/memoryMemory decomposition — live buffer versus RSS versus high-water mark.
GET /debug/pprof/profile?seconds=30Full CPU profile, suitable for a flame graph.

Requirements#

RequirementDetail
CPU≥ 0.5 core per 1 k points/second of ingest, so flushes are not starved.
Memory1.5 × rss_peak from the formula above.
Allocator environmentMALLOC_ARENA_MAX=2 and MALLOC_TRIM_THRESHOLD_=134217728 in every non-development deployment.
DiskRoughly 1 GB per 40–60 GB of raw telemetry, plus ~23 % again for the index sidecar and transient space for one compaction merge.
HeadroomThe flush peak must stay ≤ 65 % of the memory limit across at least three flush cycles.

Known limitations#

LimitationImpactWorkaround
The in-memory buffer is unboundedResident memory grows with ingest rate × block duration and does not come down until a flush. A sustained rate that fits at 100 k points/s can OOM at 300 k. The WAL does not help — it bounds crash loss, not memory.Lower storage.block_duration_secs; set the allocator variables; watch parqtel_process_rss_bytes; size from the formula.
Log and trace scans decode every columnOnly the metrics scan projects columns, so wide log and trace queries are slower and cost more memory than the row counts suggest.Narrow the time window, and pre-filter with index-backed selectors rather than scanning everything.
wal_sync_mode = "always" is expensiveAn fsync per record adds real I/O cost at high write rates.Use interval with a tuned ingest.wal_sync_interval_ms unless you need the strongest guarantee.
Compaction budget is finitecompaction_max_merges_per_pass (default 8) bounds work per cycle; a cluster producing small blocks faster than that accumulates them, raising file count and scan fan-out.Raise the budget or raise max_rows_per_block.
Traces are not compactedTrace blocks accumulate until retention removes them, so wide trace scans degrade relative to metrics at the same volume.Keep trace queries narrow; shorten trace retention.
The block index is not bounded by retentionIndex size tracks block creation rate (~0.3 GB/day at ~32 blocks/minute) and is roughly 23 % of the data it describes.Prefer fewer, larger blocks; watch parqtel_index_sidecar_bytes.
Full-block scans do not benefit from projection muchColumn projection pays −6 % to −28 % depending on row-group count, not the ≥ 30 % originally targeted.Filter by time and metric name first; projection cannot fix a query that genuinely needs every row.
Throughput figures come from one machineThe absolute numbers will not transfer to your hardware, storage, or cardinality.Re-measure; rely on the ratios and the memory model instead.
