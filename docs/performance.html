Performance

Every number below was measured against a running build, and says how. Where a proposed optimisation was measured and failed, that is recorded too rather than quietly dropped.

↗

Method and raw results: docs/benchmarks/PERFORMANCE.md. Harnesses: parqtel-core/examples/bench_bloom.rs (pruning), parqtel-server/examples/perf_bench.rs (end-to-end), parqtel-query/examples/bench_label_values.rs (autocomplete). Reproduce with cargo run --release --example <name>.

Block pruning

Rows are written grouped by metric name, so a row group's metric_name and service_name statistics are exact. The reader uses them to skip whole row groups before decoding anything. Benchmark: 200 metrics × 500 points in one block (100 000 rows), querying one metric of 200.

Statistics versus bloom filters

The decisive measurement — a three-way comparison on the same block shape:

ConfigurationBlock sizeWriteQuery
Neither (blocks written before the change)1.29 MB38 ms30.33 ms
Row-group statistics only1.47 MB55 ms2.34 ms
Statistics + bloom filter1.49 MB42 ms2.49 ms

12.1× faster queries for 14 % more bytes, from statistics alone. Adding a bloom filter on top moves the query by nothing measurable (2.34 → 2.49 ms is noise) and costs a further ~2 % size — so bloom filters are kept only as a fallback for blocks whose statistics are absent or truncated.

A query for a metric that is not in the block costs 0.02 ms instead of 30 ms: nothing is decoded at all, because the candidate set is empty before a reader is even built.

Service-level pruning

Multi-tenant shape — one metric, eight services, one row group each, querying service.name="svc-3":

TimeRows decoded
Without the service predicate2.05 ms4 000 (whole block)
With service pruning0.43 ms500

4.8×, entirely the service dimension — metric-only pruning cannot help there, because all eight row groups hold the same metric.

ℹ

The original target was "≥ 30 % for all three signals". It is not met, and the target is now wrong: it was written before row-group pruning landed, so a typical query decodes a single row group and the skipped columns were never where the time went. Projection pays in proportion to how many row groups a query must read. Log and trace scans are not projected at all.

Time-range pruning

The earlier series — multi-row-group blocks (~25 K rows) plus timestamp statistics:

BenchmarkBeforeAfterΔ
Ingest (decode + buffer push)~570 K pts/s~550 K pts/s≈ flat (±3 % noise)
Flush (50 K pts → Parquet)~840 K pts/s~830 K pts/s≈ flat (compression-bound)
Scan (full range, 600 K pts)~4.58 M pts/s~6.40 M pts/s+39 %
Query (full range, executor)~1.99 M pts/s~1.95 M pts/s≈ flat
Narrow scan (pruned to 25 K pts)n/a15–16 ms/opnew capability
Narrow query (pruned)n/a~26 ms/op11.9 M pts/s effective

The full-range query is unchanged because executor-side grouping and downsampling dominate once scanning is fast. The blocking-pool change below is at parity by design: the old code held the ingest mutex across the whole batch including synchronous Parquet writes — poor latency, but not throughput, since the work was serialised anyway. The win is isolation: no async worker is ever parked on disk I/O, which prevents p99 spikes rather than raising the mean.

Query evaluation

ChangeWorkloadBeforeAfterΔ
Prepared log/trace queries20 000 rows1.000 s4.881 ms205×
Query CPU off the runtime4 concurrent queries11.48 s3.26 s3.50×
Arc-shared labels + hashed group keys300 series × 400 points × 20 000 steps3.01 s0.438 s6.9×
Streaming step evaluationwide panel168.0 MB resident109.9 MB−35 % peak
  • Prepared queries (205×). Log and trace search evaluated the query once per row — a regex compile per =~ clause per row, a lowercase of the whole body per search term per row. Compiling costs ~1–10 µs against ~10 ns for the match, so setup dominated by three orders of magnitude. A prepared query moves all of it to a one-time new(), with an allocation-free ASCII-case-folded substring scan.
  • Blocking pool (3.5×). Evaluation runs on spawn_blocking, so a wide range query cannot starve an async worker. Single-query latency is unchanged (2.92 s → 2.87 s) — the gain is concurrency.
  • Shared labels (6.9×). Label sets are shared behind an Arc instead of being cloned per series per step — at 1 000 series × 1 000 steps that was ~20 M string allocations producing identical answers 1 000 times over. Aggregation groups are keyed by fingerprint, with the group's label set built once per distinct group.
  • Streaming steps (−35 %). Each step is folded into the response as it is produced rather than every step being retained, so peak memory is one step's vector. Measured on a 56.6 MB result.

Label-value autocomplete

The query builder must never enumerate a high-cardinality label. Worst case: 100 000 distinct user_id values across 300 K buffered points.

PathLatency (best of 20)Payload per keystroke
Bounded top-10, no prefix — buffer walk, newest-first, stop at 10~1.2 µs10 values
Bounded top-10, prefix user-099 — server-side starts_with~1.2 µs10 values
Full enumeration (unbounded dropdown)~15.6 ms100 000 values

~13 000× faster and 10 000× less data per keystroke. The flush-time per-field index is capped at 10 K values, so even cold (buffer-drained) lookups are bounded; the API clamps limit to 100.

RatioThe sidecar is 23 % of the data it describes, growing linearly at ~0.3 GB/day and not bounded by retention

metric_names is 55 % of the sidecar, because the same name is stored once per block. A per-block bloom filter over names would cut ~13 % of total storage — sound, but a sidecar format change needing a read-old/write-new story, so it is deliberately not built. Full breakdown in storage.

Measured and rejected

⚠

A series dictionary for the labels column was measured at 0.0 % benefit: 810 614 B versus 810 678 B. The premise was false — Parquet dictionary-encodes string columns by default, so the dictionary the proposal would add already exists. It was dropped rather than shipped as a no-op.

Reproducing

# End-to-end ingest / flush / scan / query
cargo run --release -p parqtel-server --example perf_bench

# Row-group pruning (statistics vs bloom vs neither)
cargo run --release -p parqtel-core  --example bench_bloom

# Label-value autocomplete
cargo run --release -p parqtel-query --example bench_label_values

# Live index footprint
curl -s localhost:9090/metrics | grep -E 'parqtel_index_sidecar_bytes|parqtel_storage_(blocks|bytes)'

All figures are from a single machine in release builds. Re-measure on your own hardware, storage and cardinality before quoting them in a capacity plan — the ratios travel better than the absolute numbers.
