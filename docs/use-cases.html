Use Cases & Comparisons#

This page helps you decide whether Parqtel fits your environment. It covers the scenarios Parqtel is built for, how it compares with established observability backends, and — just as importantly — when you should choose something else.

Where Parqtel fits#

Parqtel is a strong fit when you value long retention, low cost, and simple operations more than the lowest possible query latency.

Look elsewhere when you need sub-second alerting over a very large number of active series, or horizontal scale-out across a cluster with built-in multi-tenancy.

Recommended use cases#

Low-cost archiving#

Stream OpenTelemetry data into Parquet for long-term storage. Columnar compression typically reduces telemetry to roughly 10–20× smaller than a row-oriented time-series database, so months of history fit on commodity disk.

Good for: satisfying retention requirements, capacity trend analysis, post-incident forensics over long windows.

Edge and IoT observability#

The container image is about 15 MB and the binary has no runtime dependencies, so Parqtel runs comfortably on resource-constrained devices. Telemetry can stay local-first, with no cluster to manage.

Good for: retail stores, industrial gateways, remote sites with poor connectivity, ARM single-board computers.

Log-to-metric pipelines#

The pipeline API accepts declarative YAML definitions that describe extracting metrics from high-volume logs — for example, turning Nginx access logs into request-rate metrics without changing the application. In v0.3.1 the shipped server validates and stores these definitions but does not execute them, so no derived metric is produced yet. Today, downsample at the Collector (for example with a metrics connector) if you need log-derived metrics.

Good for (once executed): legacy applications you cannot re-instrument, cost reduction by downsampling noisy logs into metrics.

AI-assisted incident response#

The included Model Context Protocol (MCP) servers expose live queries, logs, traces, and alerts as tools that an AI assistant can call. Instead of pasting dashboards into a chat window, the assistant can investigate directly.

Good for: accelerating root-cause analysis, generating first-draft incident write-ups, answering "what changed?" questions.

Serverless and ephemeral workloads#

Ingest telemetry from short-lived compute such as AWS Lambda or Cloud Run without running a heavy backend. Parqtel accepts standard OTLP, so the platform's built-in exporter is enough.

Good for: function-as-a-service fleets, batch jobs, bursty workloads.

Parqtel versus Prometheus#

Prometheus remains the better choice for high-cardinality real-time alerting, where its in-memory index and short query latency matter. Parqtel accepts the same OTLP data and answers PromQL-compatible queries, but trades some query responsiveness for dramatically cheaper long-term retention.

A common pattern is to run both: Prometheus for the live 15 minutes, Parqtel for the archive, with Grafana pointed at each. Prometheus can also scrape Parqtel's /metrics endpoint to monitor Parqtel itself.

Parqtel versus Grafana Loki#

Loki indexes labels only and stores log bodies in object storage, making it very efficient for log search at scale. Parqtel stores logs in columnar form alongside metrics and traces, so a single query can correlate all three signals for one trace without joining two systems.

Choose Parqtel when correlation across signals matters more than raw log ingest volume. Choose Loki when logs are your dominant workload.

Parqtel versus VictoriaMetrics#

VictoriaMetrics is a high-performance, horizontally scalable time-series database with strong compression and full PromQL support. It will generally out-perform Parqtel on large metric workloads and can scale across nodes.

Choose Parqtel when you want traces and logs in the same store, want to keep the deployment to a single binary, or need edge-friendly resource usage.

Compatibility promises#

Parqtel is designed to slot into an existing observability stack rather than replace it wholesale.

Existing assetCompatibility
OpenTelemetry SDKs and CollectorsSend OTLP over gRPC or HTTP with no plugin or exporter change.
Prometheus query API clients/api/v1/query and /api/v1/query_range follow the Prometheus response shape.
GrafanaUse the SimpleJSON datasource plugin (or Infinity); the metric query path works, while /annotations and /tag-values are stubs today.
Existing PromQLMost queries work unchanged; the differences are documented exhaustively in the Query Reference.
Backup toolingBlocks are immutable files; any file-copy or snapshot tool works.

Performance at a glance#

On commodity hardware, Parqtel sustains roughly 1,000 samples/second across metrics, logs, and traces combined, with ingest latency around 4.4 ms per batch (p50) and instant queries returning in roughly 12.7 ms (p50). Queries served from the in-memory buffer return in about 1.7 ms.

These figures are a starting point for sizing, not a guarantee. Full methodology and results are in Performance & Scaling.
