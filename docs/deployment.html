Deployment

From a single container to production Kubernetes — Parqtel deploys anywhere a Linux binary or OCI image runs. This page tracks chart v0.3.1.

Container image

Published to GitHub Container Registry, multi-arch (linux/amd64, linux/arm64), cosign-signed with an SBOM and provenance attestation.

docker run -d \
  --name parqtel \
  -p 8080:8080 \
  -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:0.3.1

docker exec parqtel healthcheck ready      # bundled probe binary (no shell in the image)
curl -f http://localhost:8080/ready

The runtime is FROM scratch, not distroless. The multi-stage build assembles a minimal glibc/libgcc rootfs in a dedicated runtime-libs stage and copies in only what the binary and a std-only probe need — ~15 MB, no shell, no package manager. That is why the healthcheck is a compiled probe binary rather than curl.

Local development

Docker Compose

Brings up Parqtel, Grafana (auto-provisioned), Prometheus (scraping Parqtel) and a load generator. Network isolation splits frontend (user-facing) from backend (internal).

ServicePortDescription
parqtel9090Observability server (HTTP) + 4317 OTLP gRPC
grafana3000Dashboards, pre-provisioned with Parqtel as a datasource
prometheus9091Self-monitoring scraper
load-generator—Synthetic ingest
mcp-*3001–3007MCP servers (commented out by default)
 
make dev-setup        # copies .env.example → .env, then docker compose up -d
make local-rebuild   # REQUIRED after source changes — rebuilds images and restarts
make local-down      # tear down
⚠

The Compose dev profile sets wal_enabled = false, so the local stack runs with the metrics and traces WALs off and no background flush worker. That is a development convenience, not a recommendation — the binary default and the chart default are both true.

Kubernetes (Helm)

helm install parqtel charts/parqtel \
  --namespace parqtel --create-namespace \
  -f charts/parqtel/ci/full-values.yaml

kubectl -n parqtel port-forward svc/parqtel 8080:8080
curl -s localhost:8080/ready

Chart features: HPA, PDB, NetworkPolicy, Ingress, ServiceMonitor, PrometheusRule, optional kube-prometheus-stack and cert-manager sub-charts, an optional Kubernetes custom-metrics provider, and each MCP server deployable as its own pod. The whole values file is schema-validated by values.schema.json, so a typo fails helm lint rather than silently doing nothing.

Write-ahead log

The WAL keys were never rendered by the ConfigMap template before chart 0.3.1 — you could not tune segment size or fsync interval without hand-patching a ConfigMap the next helm upgrade discarded. All four are now settable:

parqtel:
  ingest:
    walEnabled: true                # metrics AND traces
    logWalEnabled: true             # logs
    walMaxSegmentBytes: 16777216    # 16 MiB — overrides the binary's 64 MiB default
    walSyncIntervalMs: 1000         # fsync period; lower = smaller loss window
ℹ

The chart default of 16 MiB is deliberately tighter than the binary's 64 MiB: it bounds the largest single segment's replay cost and caps the file the writer must fsync, at the price of more segment churn. The chart does not render wal_sync_mode or max_inflight_flushes; use extraEnv for those.

Probes

livenessProbe, readinessProbe and startupProbe are configurable and their defaults reproduce the previous hardcoded values exactly — so upgrading changes nothing until you edit them.

ProbeEndpointDefaultWhat it checks
liveness/healthdelay 10 s, period 30 s, timeout 5 s, 3 failuresThe process is alive. Static 200.
readiness/readydelay 5 s, period 10 s, timeout 3 s, 3 failuresStorage is usable — reads block-index metadata and returns 503 on failure.
startup/healthperiod 5 s, 30 failures → 150 sGoverns the startup window, and disables liveness until it passes.
⚠

Why startup needs a budget that can move. On start Parqtel replays whatever the WAL did not flush, and that replay is proportional to unflushed WAL — so it is slow exactly when the pod is least healthy. The hardcoded budget was 150 s. An install returning with a large WAL replay exceeds it, gets killed by the liveness probe mid-replay, and restarts with an even larger replay. If that happens, raise startupProbe.failureThreshold (or periodSeconds) — do not delete the startup probe, because that hands the same work to the liveness probe, which has a much smaller budget. Each probe can be set to {} to disable.

# Give a recovering pod up to 10 minutes to replay its WAL.
startupProbe:
  httpGet: { path: /health, port: http }
  periodSeconds: 5
  failureThreshold: 120

Production values

replicaCount: 1            # >1 requires shared storage (NFS/EFS) — see below

image:
  repository: ghcr.io/parqtel/parqtel-oss
  tag: ""                    # defaults to the chart appVersion

resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits:   { cpu: "2",   memory: 2Gi }

persistence:
  enabled: true
  size: 50Gi
  storageClassName: gp3
  accessMode: ReadWriteOnce

extraEnv:
  - name: MALLOC_TRIM_THRESHOLD_
    value: "134217728"      # 128 MiB — see the sizing page

autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70

networkPolicy: { enabled: true }

mcp:
  parqtel:
    enabled: true
    env:
      PARQTEL_API_URL: "http://parqtel:8080"
⚠

Replicas > 1 need shared storage. Each replica owns its own blocks, its own index.json and its own WAL. With ReadWriteOnce and one replica per node you get N independent stores — correct, but queries and the built-in console only see the pod you reach. Use a shared RWX volume, or route queries to a specific replica.

Overlays ship for minimal, default, dev, production, ci, orbstack and load-test. A 4 GiB constrained profile is at deploy/k3d-values-4gb.yaml; local k3d workflows run through make local-k3d-up.

Argo Rollouts

Parqtel is a drop-in metrics backend for Argo Rollouts. Because it exposes a Prometheus-compatible query API, the stock Argo Rollouts Prometheus provider queries Parqtel with no custom code — you only point the provider's address at Parqtel.

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: parqtel-red
spec:
  args:
  - name: service            # OTel service.name under test
  metrics:
  - name: error-rate
    initialDelay: 1m         # let RED metrics accumulate before the first check
    interval: 30s
    count: 10                # ~5 minutes of sampling
    failureLimit: 1
    successCondition: "result[0] < 0.01"
    failureCondition: "result[0] > 0.05"
    provider:
      prometheus:
        address: http://parqtel.parqtel.svc.cluster.local:8080
        query: |
          sum(sum_over_time(traces_service_errors_total{service.name="{{args.service}}"}[5m]))
          /
          sum(sum_over_time(traces_service_requests_total{service.name="{{args.service}}"}[5m]))
↗

Zero-config RED. If your app exports OTel traces, Parqtel auto-derives traces_service_{requests,errors,duration_ms}_total per service.name and operation from server spans — no hand-written instrumentation or recording rules.

To gate on only the canary, make the canary revision export a distinguishing label — set the OTel service.name to include the revision, or filter on a revision resource attribute. Argo Rollouts can pass the pod hash via valueFrom.podTemplateHashValue.

Two limitations to plan around: the Prometheus provider gates on metrics only — Parqtel's log and trace search and cross-signal pipelines are not reachable through it. And /api/v1/query looks back 5 minutes, so use initialDelay or provider.prometheus.rangeQuery for an explicit window. If a query returns no series, result[0] is undefined and the measurement errors.

Examples: examples/argo-rollouts/. Full guide: docs/ARGO_ROLLOUTS.md.

systemd (bare metal)

sudo useradd -r -s /bin/false parqtel
sudo mkdir -p /var/lib/parqtel/{data,logs} /etc/parqtel
sudo chown -R parqtel:parqtel /var/lib/parqtel

sudo install -m 0755 target/release/parqtel /usr/local/bin/parqtel
sudo install -m 0644 config/default.toml /etc/parqtel/parqtel.toml
sudo install -m 0644 deploy/systemd/parqtel.service /etc/systemd/system/

sudo systemctl daemon-reload && sudo systemctl enable --now parqtel
journalctl -u parqtel -f | grep -E 'WAL replay|reconciled|listening'

Production recommendations

Storage

Prefer SSDs — Parquet rewards fast sequential reads. Budget (rate × retention_days) / 20 for zstd at default level, and add the block index: measured at 23 % of data volume, growing ~0.3 GB/day and not bounded by retention.

Memory

Size from the formula, not a default — memory scales with buffered points, and the buffer is unbounded. Set MALLOC_ARENA_MAX=2 and MALLOC_TRIM_THRESHOLD_=134217728 or RSS will ratchet to the high-water mark and never return.

Probes

Use /ready for readiness and load-balancer health checks — /health is static and will happily mark a pod ready while its storage is failing.

Networking

There is no authentication. Terminate TLS and authenticate at a reverse proxy or service mesh before exposing 8080 or 4317. Match the proxy body limit to ingest.max_body_size.

Monitoring

Scrape /metrics. Watch parqtel_process_rss_bytes, parqtel_buffer_points, parqtel_flush_duration_seconds, parqtel_index_sidecar_bytes, parqtel_ingest_lock_wait_seconds.

Backup

Blocks are immutable, so a live copy is safe. Back up index.json for fast startup — but a lost or stale sidecar repairs itself at startup by reconciliation, so it is an optimisation, not a requirement.

Profiling

/debug/pprof/* is off by default and 404s until enabled. Turn it on temporarily and restrict it with a NetworkPolicy.

Supply chain

Images are multi-arch, cosign-signed, SBOM- and provenance-attested, Trivy-scanned (report-only) and CodeQL-analyzed in CI. Verify signatures on pull from GHCR.

Post-deploy verification

curl -sf localhost:8080/health              # {"status":"ok"}
curl -sf localhost:8080/ready               # {"status":"ready"}  |  503 if storage is broken
curl -s  localhost:8080/api/v1/stats | jq   # blocks, rows, disk bytes, index size per signal
curl -s  localhost:8080/metrics | grep -E 'wal|flush|index_sidecar|buffer_points'
kubectl -n parqtel logs deploy/parqtel | grep -E 'WAL replay|reconciled|listening'
