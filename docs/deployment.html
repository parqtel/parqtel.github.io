Deploy#

Parqtel runs anywhere a Linux binary or OCI image runs — from a single container on a laptop to a production Kubernetes StatefulSet. This guide covers each deployment target, the settings that matter in production, and how to verify a deployment actually works.

The current chart version is v0.3.1.

Deployment options#

↗

Port difference: a plain docker run serves Parqtel on :8080, but the bundled Docker Compose profile publishes it on :9090 (because Prometheus claims :9090 in that stack and is moved to :9091). Check which one you are running before debugging a connection failure.

Prerequisites#

TargetRequirements
DockerDocker Engine 20.10+; linux/amd64 or linux/arm64.
Docker ComposeDocker Compose v2.
KubernetesHelm 3, a StorageClass that supports ReadWriteOnce, and a namespace.
systemdA Linux host with systemd; a release binary and a data directory.
AllA decision about how to authenticate access — Parqtel ships without authentication.

Docker#

The image is published to GitHub Container Registry, multi-arch for linux/amd64 and linux/arm64, and is signed with an SBOM and provenance attestation. There is no Docker Hub mirror.

docker run -d \
  --name parqtel \
  -p 8080:8080 \
  -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:0.3.1

Verify:

docker exec parqtel healthcheck ready     # bundled probe binary
curl -f http://localhost:8080/ready

Container properties#

PropertyValue
Base imagescratch — no shell, no package manager
Image size~15 MB
UserNon-root, UID/GID 65532
FilesystemRead-only root filesystem; all capabilities dropped
Writable paths/data (mount), /tmp

Because there is no shell in the image, health checks use a bundled compiled probe binary rather than curl. Adjust your own probes accordingly — docker exec parqtel healthcheck ready is the equivalent of a ready check.

Docker Compose (full stack)#

Brings up Parqtel, Grafana (pre-provisioned with Parqtel as a datasource), Prometheus (scraping Parqtel), and a synthetic load generator.

ServicePortDescription
parqtel9090Observability server (HTTP), plus 4317 for OTLP gRPC
grafana3000Dashboards, pre-provisioned with Parqtel as a datasource
prometheus9091Self-monitoring scraper
load-generator—Synthetic ingest
mcp-*3001–3007MCP servers (commented out by default)
make dev-setup          # copies .env.example → .env, then docker compose up -d
make local-rebuild      # REQUIRED after source changes
make local-down         # tear down
↗

The Compose profile is not a production configuration. It sets wal_enabled = false, so the local stack runs with the metrics and traces write-ahead logs off and no background flush worker. That is a development convenience. Both the binary default and the Helm chart default are true.

Kubernetes (Helm)#

helm install parqtel charts/parqtel \
  --namespace parqtel --create-namespace \
  -f charts/parqtel/ci/full-values.yaml

kubectl -n parqtel port-forward svc/parqtel 8080:8080
curl -s localhost:8080/ready

The chart includes HPA, PDB, NetworkPolicy, Ingress, ServiceMonitor, and PrometheusRule resources, optional sub-charts, an optional custom-metrics provider, and each MCP server deployable as its own pod. The values file is schema-validated, so a typo fails helm lint rather than silently doing nothing.

Write-ahead log settings#

Before chart v0.3.1 these keys were not rendered, so they could not be tuned without hand-editing a ConfigMap that the next helm upgrade would discard. All four are now settable:

parqtel:
  ingest:
    walEnabled: true              # metrics AND traces
    logWalEnabled: true           # logs
    walMaxSegmentBytes: 16777216  # 16 MiB — overrides the binary's 64 MiB default
    walSyncIntervalMs: 1000       # fsync period; lower = smaller loss window
↗

The chart default of 16 MiB is deliberately tighter than the binary's 64 MiB: it bounds the largest single segment's replay cost and caps the file the writer must sync, at the price of more segment churn. The chart does not render wal_sync_mode or max_inflight_flushes; set those through extraEnv.

Probes#

livenessProbe, readinessProbe, and startupProbe are all configurable. Their defaults reproduce the previous hardcoded values exactly, so upgrading changes nothing until you edit them.

ProbeEndpointDefaultWhat it checks
liveness/healthdelay 10s, period 30s, timeout 5s, 3 failuresThe process is alive. Static success.
readiness/readydelay 5s, period 10s, timeout 3s, 3 failuresStorage is usable — reads block-index metadata, returns 503 on failure.
startup/healthperiod 5s, 30 failures (150s budget)Governs the startup window and disables liveness until it passes.
↗

Why the startup budget needs to be tunable. On start, Parqtel replays whatever the write-ahead log did not flush, and that replay is proportional to unflushed log size — so startup is slowest exactly when the pod is least healthy. The old hardcoded budget was 150 seconds. An install returning with a large log replay exceeds it, is killed by the liveness probe mid-replay, and restarts with an even larger replay. If this happens, raise startupProbe.failureThreshold (or periodSeconds). Do not delete the startup probe — that hands the same work to the liveness probe, which has a much smaller budget. Each probe can be set to {} to disable it.

# Give a recovering pod up to 10 minutes to replay its write-ahead log.
startupProbe:
  httpGet: { path: /health, port: http }
  periodSeconds: 5
  failureThreshold: 120

Production values#

replicaCount: 1                  # >1 requires shared storage — see below

image:
  repository: ghcr.io/parqtel/parqtel-oss
  tag: ""                        # defaults to the chart appVersion

resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits:   { cpu: "2",  memory: 2Gi }

persistence:
  enabled: true
  size: 50Gi
  storageClassName: gp3
  accessMode: ReadWriteOnce

extraEnv:
  - name: MALLOC_TRIM_THRESHOLD_
    value: "134217728"           # 128 MiB — see Memory sizing

autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70

networkPolicy:
  enabled: true

mcp:
  parqtel:
    enabled: true
    env:
      PARQTEL_API_URL: "http://parqtel:8080"
↗

Replicas greater than 1 need shared storage. Each replica owns its own blocks, its own block index, and its own write-ahead log. With ReadWriteOnce and one replica per node you get N independent stores — correct, but queries and the built-in console only see the pod you happen to reach. Use a shared ReadWriteMany volume, or route queries to a specific replica.

Overlay profiles ship for minimal, default, dev, production, ci, orbstack, and load-test. A 4 GiB constrained profile is provided for local k3d workflows.

Argo Rollouts#

Parqtel is a drop-in metrics backend for Argo Rollouts: because it exposes a Prometheus-compatible query API, the stock Prometheus analysis provider queries Parqtel with no custom code. You only point the provider's address at Parqtel.

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: parqtel-red
spec:
  args:
    - name: service            # OTel service.name under test
  metrics:
    - name: error-rate
      initialDelay: 1m         # let RED metrics accumulate first
      interval: 30s
      count: 10                # ~5 minutes of sampling
      failureLimit: 1
      successCondition: "result[0] < 0.01"
      failureCondition: "result[0] > 0.05"
      provider:
        prometheus:
          address: http://parqtel.parqtel.svc.cluster.local:8080
          query: |
            sum(sum_over_time(traces_service_errors_total{service.name="{{args.service}}"}[5m]))
            /
            sum(sum_over_time(traces_service_requests_total{service.name="{{args.service}}"}[5m]))

This works with zero custom instrumentation, because Parqtel derives RED metrics automatically from server spans. See Ingest Telemetry.

Three limitations to plan around:

  1. The Prometheus provider gates on metrics only — log search, trace search, and cross-signal pipelines are not reachable through it.
  2. /api/v1/query looks back 5 minutes, so use initialDelay or an explicit range window.
  3. If a query returns no series, the measurement errors because result[0] is undefined. Make sure the service is actually emitting spans before the first evaluation.

To gate on the canary revision only, give the canary a distinguishing label — either include the revision in service.name, or filter on a revision resource attribute. Argo Rollouts can supply the pod hash.

systemd (bare metal)#

sudo useradd -r -s /bin/false parqtel
sudo mkdir -p /var/lib/parqtel/{data,logs} /etc/parqtel
sudo chown -R parqtel:parqtel /var/lib/parqtel

sudo install -m 0755 target/release/parqtel /usr/local/bin/parqtel
sudo install -m 0644 config/default.toml /etc/parqtel/parqtel.toml
sudo install -m 0644 deploy/systemd/parqtel.service /etc/systemd/system/

sudo systemctl daemon-reload
sudo systemctl enable --now parqtel

# Confirm startup completed
journalctl -u parqtel -f | grep -E 'WAL replay|reconciled|listening'

Production recommendations#

Storage#

  • Prefer SSDs — Parquet rewards fast sequential reads.
  • Budget roughly (ingest rate × retention days) / 20 for Zstd at the default level.
  • Add the block index on top: measured at ~23% of data volume, growing about 0.3 GB/day, and not bounded by retention.

Memory#

  • Size from the performance sizing model, not from a default — memory scales with buffered points, and the buffer is unbounded.
  • Set MALLOC_ARENA_MAX=2 and MALLOC_TRIM_THRESHOLD_=134217728 (128 MiB), or resident memory will ratchet to its high-water mark and never be returned.

Probes#

Use /ready for readiness and load-balancer health checks. /health is static and will happily mark a pod ready while its storage is failing.

Networking#

There is no authentication. Terminate TLS and authenticate at a reverse proxy or service mesh before exposing 8080 or 4317. Match the proxy's body limit to ingest.max_body_size so large batches are not rejected at the edge.

Monitoring#

Scrape /metrics and alert on:

MetricWatch for
parqtel_process_rss_bytesMemory ratcheting toward the limit
parqtel_buffer_pointsBuffer growth outpacing flush rate
parqtel_flush_duration_secondsFlush slowdowns
parqtel_index_sidecar_bytesIndex growth relative to data
parqtel_ingest_lock_wait_secondsIngest contention

Backup#

Blocks are immutable, so a live copy is safe. Back up the block index for faster startup — but a lost or stale sidecar repairs itself at startup, so it is an optimisation rather than a requirement. See Back Up, Restore & Upgrade.

Profiling#

The /debug/pprof/* endpoints are off by default and return 404 until enabled. Enable them temporarily and restrict access with a NetworkPolicy.

Supply chain#

Images are multi-arch, signed, SBOM- and provenance-attested, and scanned. Verify signatures on pull if your policy requires it.

Post-deploy verification#

Run all five checks after any deployment:

# 1. Liveness
curl -sf localhost:8080/health          # {"status":"ok"}

# 2. Readiness — 503 means storage is broken
curl -sf localhost:8080/ready           # {"status":"ready"}

# 3. Storage is being written
curl -s localhost:8080/api/v1/stats | jq

# 4. Background subsystems are healthy
curl -s localhost:8080/metrics | grep -E 'wal|flush|index_sidecar|buffer_points'

# 5. Startup completed cleanly (Kubernetes)
kubectl -n parqtel logs deploy/parqtel | grep -E 'WAL replay|reconciled|listening'

Troubleshooting#

SymptomCauseResolution
Cannot reach :8080 after ComposeCompose publishes Parqtel on :9090.Use :9090 with Compose, :8080 with plain docker run.
Pod restarts repeatedly during startupStartup probe budget exceeded by write-ahead log replay.Raise startupProbe.failureThreshold; do not remove the probe.
Pod marked ready but queries failReadiness pointed at /health (static).Point readiness at /ready.
helm upgrade silently reverts settingsValues were hand-patched into a ConfigMap.Set them in values.yaml; the ConfigMap is regenerated on upgrade.
Only one replica's data is visibleEach replica owns a separate store.Use a shared ReadWriteMany volume, or query a specific replica.
Memory grows and never fallsAllocator high-water mark retained.Set MALLOC_TRIM_THRESHOLD_=134217728 and MALLOC_ARENA_MAX=2.
