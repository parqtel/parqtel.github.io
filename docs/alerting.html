Alerting#

Parqtel includes a built-in alerting engine: you define rules in YAML, and Parqtel evaluates them on a fixed interval, tracks each alert through a state machine, and routes notifications to webhooks. No external alerting component is required.

How alerting works#

Every 15 seconds (configurable via server.alert_interval_secs), the evaluation loop:

  1. Parses each enabled rule's query.
  2. Loads the matching series over a trailing window of query.lookback_delta_ns (5 minutes by default — the same window you see in the console).
  3. Thresholds the newest raw sample of every result series.
  4. Creates or updates one alert instance per series, fingerprinted by the rule id plus the series' labels.

The loop does not run the full expression engine. In v0.3.1 it builds the query plan without a step, so rate(), increase(), aggregations, and histogram_quantile() are parsed but not applied to the value being thresholded. See Step 2 before writing rules.

Prerequisites#

  • Parqtel running with alerting enabled (on by default).
  • A directory for rule files — alerts.rules_dir, default rules.
  • For notifications: an HTTP endpoint that accepts a JSON POST.
  • Metrics for your rules to query (rules are metric-only today). If you want RED metrics without writing instrumentation, see Ingest Telemetry.

Step 1 — Write your first rule#

Rules are YAML files in alerts.rules_dir, one rule per --- document. The directory is read non-recursively at startup; there is no file watcher, so add or edit rules and restart, or create them at runtime with POST /api/v1/rules.

Create rules/http-errors.yaml:

id: http-error-ratio-high         # unique and stable — the alert instance prefix
name: HTTP error ratio high
signal: metrics                   # accepted for compatibility; see note below
query: "http_error_ratio"         # a gauge exported by your app or Collector
condition:
  type: threshold                 # only "threshold" is implemented
  operator: ">"                   # > >= < <= == !=
  value: 0.05                     # the value to compare against
  for_duration_secs: 120          # must hold this long before Firing
severity: warning                 # info | warning | critical
enabled: true
labels:
  team: platform
annotations:
  summary: "HTTP error ratio is {{ $value }} on {{ $labels.service }}"
  runbook: "https://wiki.internal/runbooks/http-errors"

This example assumes the application exports http_error_ratio as a gauge. The alert loop thresholds raw samples, so a counter or a rate(...) expression will not give you an error rate — see Step 2.

↗

signal is accepted but only metrics is evaluated. The evaluation loop parses every rule query with the metrics query-plan path, so a rule declaring signal: logs or signal: traces is still evaluated against metrics and will normally match nothing. Write metric rules today.

Step 2 — Write queries the evaluator actually applies#

This is where most alerting mistakes happen. The alert loop uses the legacy query-plan path with no step, so it thresholds the newest raw sample of each matching series. Range functions and aggregations are parsed but not applied to that value in v0.3.1.

Rule queryWhat the evaluator actually does
queue_depthThresholds the newest queue_depth sample for each series.
kube_pod_status_phase{phase="Pending"}Thresholds the series' 1/0 value; use > 0.
traces_service_duration_msThresholds the duration of the latest server span, one instance per service/operation series.
traces_service_errors_totalThresholds 1 (error) or 0 (success) for the latest span. Use > 0.
rate(errors_total[5m])Parses, but thresholds the newest raw counter value, not a rate.
increase(errors_total[5m])Same: the raw counter value is thresholded.
sum by (service) (rate(errors_total[5m]))Not usable: the inner rate(...) is treated as a metric name, so the rule finds no series.
sum(rate(errors_total[5m]))Same: no series.
histogram_quantile(0.99, ...)Parses, but the loop thresholds a raw bucket sample; no quantile is computed.

Malformed or unmatched queries are silently skipped by the loop — there is no rule error status. Before relying on a rule, check that its selector returns series with GET /api/v1/query?query=<selector>.

by/without grouping can merge series for label selection, but it does not sum or average their values: the newest sample still wins. Do not use grouping as a substitute for an aggregation.

What to alert on instead#

Alert on a gauge whose current value is the signal you care about: queue depth, in-flight requests, utilisation, replica shortfall, a status condition, or a precomputed rate/ratio.

For rates and ratios, compute the value before it reaches Parqtel — for example with an OpenTelemetry Collector processor or your own exporter — and alert on the resulting gauge. Recording rules are the intended in-product mechanism, but they are stored and not executed in v0.3.1, so they cannot supply the series today.

Latency alerts#

The derived duration metric is a gauge measured in milliseconds, one sample per server span. Threshold it directly:

id: latest-span-slow
name: Latest server span is slow
query: "traces_service_duration_ms"
condition:
  type: threshold
  operator: ">"
  value: 1000             # milliseconds
  for_duration_secs: 0
severity: warning

This fires on the latest span for each service/operation series, not on an average. A single slow request can fire it, and the next fast request clears it. For sustained latency, precompute a rolling average or a histogram-backed gauge outside Parqtel and alert on that.

Error alerts#

traces_service_errors_total is 1 for an error span and 0 otherwise, again one sample per span:

id: latest-span-errored
name: Latest server span errored
query: "traces_service_errors_total"
condition:
  type: threshold
  operator: ">"
  value: 0
severity: warning

This is an edge trigger on the latest span, not an error-rate alert. For a rate, precompute it as a gauge.

Step 3 — Route notifications#

Notification routes map alerts to webhooks based on severity and labels.

[[alerts.notifications.routes]]
name = "platform-critical"
match_severity = "critical"          # single minimum severity, not a list
webhook_url = "https://hooks.internal/oncall"
repeat_minutes = 30

[[alerts.notifications.routes]]
name = "team-platform"
match_labels = { team = "platform" }
webhook_url = "https://hooks.internal/platform"
repeat_minutes = 120
KeyTypeDefaultDescription
nameString—Route identifier.
match_severityString"info"Minimum severity an alert must have to match this route (info, warning, or critical). The default matches every alert.
match_labelsMap{}Label matchers; all must match.
webhook_urlString—Destination for JSON POSTs.
repeat_minutesInteger240Re-notification interval while an alert keeps firing. 0 notifies once.

Step 4 — Silence alerts during maintenance#

Create a silence to suppress notifications for a known window:

curl -X POST http://localhost:8080/api/v1/alerts/silences \
  -H "Content-Type: application/json" \
  -d '{
    "name": "maintenance-2026-10-05",
    "created_by": "oncall@example.com",
    "match_labels": {"service": "checkout"},
    "starts_at": '"$(date +%s)"',
    "ends_at": '"$(($(date +%s) + 3600))"'
  }'
OperationEndpoint
List silencesGET /api/v1/alerts/silences
Create a silencePOST /api/v1/alerts/silences
Delete a silenceDELETE /api/v1/alerts/silences/{name}

Alerts still evaluate and still change state during a silence — notifications are simply suppressed.

Alert-instance responses are wrapped: {"status":"success","data":[…]}. Alert id values are ULIDs generated by the store — they are not the rule id. Both acknowledge and resolve expect a JSON body (it may be {}; by names the actor).

# See what is firing (ids are ULIDs, not rule ids)
curl -s http://localhost:8080/api/v1/alerts | jq '.data[] | {id, rule_id, state, severity}'

# Acknowledge a known issue
curl -X POST http://localhost:8080/api/v1/alerts/<ulid>/acknowledge \
  -H "Content-Type: application/json" -d '{"by":"oncall@example.com"}'

Recording rules#

↗

Not executed in v0.3.1. Recording-rule groups can be stored through the API, but no ruler scheduler evaluates them, so the ratio workaround below is not available yet. Until it ships, precompute the ratio as a gauge outside Parqtel (for example in an OpenTelemetry Collector processor) and threshold that gauge.

When it does run, a recording rule evaluates a ParQL expression on a schedule and writes the result back as a metric. Groups are Prometheus-style — a name, an interval, and a list of record/expr rules:

name: http_service_aggregations
interval: 1m
rules:
  - record: service:http_error_rate:rate5m
    expr: |
      sum by (service_name) (rate(http_requests_total{status=~"5.."}[5m]))
        / sum by (service_name) (rate(http_requests_total[5m]))
    labels:
      aggregation: "rate5m"

An alert rule would then threshold the recorded metric:

id: error-ratio-high
name: Error ratio high
query: "service:http_error_rate:rate5m"
condition:
  type: threshold
  operator: ">"
  value: 0.05

Built-in alert presets#

Five preset packs ship inside the binary and activate automatically when their canary metrics appear.

Pack keyCovers
kubernetesCluster-level Kubernetes health
corednsDNS resolution health
external-secretsSecret synchronization failures
service-redRequest, error, and duration rates per service
parqtelParqtel's own self-telemetry
[alerts.presets]
mode = "auto"          # auto | all | off
include = []           # e.g. ["kubernetes", "parqtel"]
exclude = []           # e.g. ["service-red"]
KeyTypeDefaultDescription
modeString"auto"auto activates a pack when its canary metrics appear; all activates every selected pack at startup; off never loads built-ins.
includeList or comma-separated string[]Include-only pack keys. Wins over exclude when both are set (a warning is logged). Unknown keys are logged and ignored.
excludeList or comma-separated string[]Pack keys to skip. Applied only when include is empty.

Or via environment variables:

export PARQTEL__ALERTS__PRESETS__MODE=auto
export PARQTEL__ALERTS__PRESETS__INCLUDE=kubernetes,parqtel
export PARQTEL__ALERTS__PRESETS__EXCLUDE=service-red
⚠

Your rules always win. Preset activation is insert-if-absent, and once a pack is activated it never deactivates. A rule from rules_dir, or a disable/delete issued through the API, always takes precedence over a built-in.

Alert tuning#

KeyTypeDefaultDescription
alerts.rules_dirString"rules"Directory of alert rule YAML files. Read non-recursively at startup; there is no file watcher.
alerts.noise_window_firingsInteger30Reserved for the noise score; no scoring pass runs in v0.3.1.
alerts.refinement_enabledBooleantrueReserved; no refinement pass runs in v0.3.1.
alerts.noise_suppression_thresholdFloat0.7Reserved; stored on rules but not evaluated in v0.3.1.

Noise scoring is not implemented in this release. The intent is to flag alerts that fire repeatedly and resolve quickly — usually a badly chosen threshold rather than a real incident — but instances are stored with a noise_score of 0 and never transition on it. Tune thresholds and condition.for_duration_secs instead.

Step 6 — Postmortem automation (not implemented)#

The [alerts.postmortem] block is parsed and validated, but no postmortem engine is wired into the server in v0.3.1 — no draft is generated when an incident resolves. The accepted keys and defaults are below, so a configuration file is forward-compatible; they have no runtime effect today.

Troubleshooting#

SymptomCauseResolution
Rule file is ignored entirelyA YAML parse error, or the file is in a subdirectory.rules_dir is loaded non-recursively. Validate the YAML and keep rules directly in the directory.
Rule never fires although the metric is clearly breachedThe query returns no series, or it composes functions (sum(rate(...)), _over_time) that the alert loop cannot plan.Run the bare selector in the console first. Simplify to a single selector; precompute derived values outside Parqtel.
rate()/increase() rule behaves like the raw counterThe alert loop does not apply range functions in v0.3.1.Alert on a precomputed rate gauge, or threshold the raw value deliberately.
An alert fires for one series but not anotherOne alert instance is created per result series.Check labels on the underlying series; grouping does not sum values in v0.3.1, so precompute a grouped series if you need one instance.
histogram_quantile rule behaves like a raw bucketThe alert loop does not apply the quantile; it thresholds the newest bucket sample.Precompute the quantile as a gauge and threshold that.
Ratio rule cannot be writtenCross-metric arithmetic is unsupported in the alert loop.Precompute the ratio as a gauge; recording rules are stored but not executed in v0.3.1.
Duplicate notificationsMultiple routes match the same alert.Narrow match_severity or match_labels.
Preset rules conflict with your ownBoth define the same rule.Presets are insert-if-absent, so yours wins — but rename to avoid confusion.
Alert fluctuates between Firing and ResolvedThreshold too close to normal variation.Raise condition.for_duration_secs, or adjust the threshold.
