Overview#

Parqtel is an observability backend that stores OpenTelemetry metrics, logs, and traces as compressed Apache Parquet files on ordinary storage. It runs as a single binary, answers Prometheus-compatible queries, and ships with a built-in web console, an alerting engine, and connectors that let AI assistants read your telemetry.

Use Parqtel when you want months of retained telemetry at a fraction of the cost and operational weight of a traditional time-series cluster — and when you want to keep using the Grafana dashboards and Prometheus queries you already have.

Why Parqtel exists#

Conventional observability backends keep recent data in a purpose-built time-series database and either drop older data or push it to a separate archive system. That design is fast, but it is expensive to run, heavy on memory, and it forces you to choose between retention and cost.

Parqtel takes a different approach: every signal is written directly to columnar files, the same format used by data warehouses and analytics engines. Columnar storage compresses far better than a row-oriented time-series database, and because the files are self-contained and immutable, a backup is a file copy and historical queries are a parallel file scan.

The trade-off is deliberate. Parqtel favours low resource usage, long retention, and simple operations over sub-second writes and sub-second queries across very large fleets. See Known limitations below for the details.

How it fits into your stack#

Flow in words:

  1. Your services send telemetry using the standard OpenTelemetry Protocol (OTLP) — either over gRPC or HTTP. No proprietary agent is required.
  2. Parqtel decodes the payload and makes it immediately queryable from an in-memory buffer, so a metric you just sent can be queried back right away.
  3. On a fixed interval, buffered data is flushed into an immutable Parquet block and acknowledged as durable.
  4. Queries read from the buffer and the blocks, so results are continuous across the boundary with no double-counting.
  5. The same stored data feeds the alerting engine, the built-in console, Grafana, and the AI connectors.

Capabilities#

AreaWhat you get
IngestionOTLP over gRPC (:4317, the OpenTelemetry SDK default) for metrics, logs, and traces. Over HTTP, metrics and logs accept protobuf or JSON; traces accept JSON only (/v1/traces, /v1/traces/json). No collector required, though you can use one.
StorageBlock-based Parquet with Zstd, Snappy, or LZ4 compression. Automatic compaction for metrics and logs, configurable retention per signal.
QueryPrometheus-compatible instant and range queries with label matching, aggregations, and over-time functions.
Log & trace searchA separate query language for searching log bodies and filtering spans by service, operation, duration, and status.
AlertingRules defined in YAML, threshold conditions, a full state machine (Inactive → Pending → Firing → Resolved), and webhook notification routing. Rules load at startup; the rules API changes them at runtime. The evaluator thresholds the newest raw sample, so alert on gauges rather than rate() expressions — see Alerting.
Derived metricsRequest/error/duration (RED) metrics are generated automatically from your spans, so service dashboards work without extra instrumentation.
Tail samplingDrop routine traces while always keeping errors and slow requests. Derived RED metrics are computed before sampling, so your metrics stay accurate.
VisualisationA built-in console at /ui, plus Grafana and Prometheus compatibility — no new dashboard tooling to learn.
AI connectorsModel Context Protocol (MCP) servers for Slack, PagerDuty, Jira, Notion, Discord, Google Docs, and Parqtel itself. Only parqtel-mcp-parqtel is wired to live data in v0.3.1; the six integration servers register tool schemas only.
OperationsHealth and readiness endpoints, self-monitoring metrics, graceful shutdown, and a small CLI for maintenance tasks.

Design goals#

GoalHow it is achieved
Minimal footprintOne static binary and a ~15 MB container image based on scratch — no shell, no runtime dependencies.
Cheap long-term storageColumnar Parquet with Zstd compression; typical telemetry compresses several times smaller than a row-oriented store.
Crash-safe writesA write-ahead log means an acknowledged write survives a process crash. See Durability & Recovery.
Prometheus compatibilityA Prometheus-compatible HTTP query API plus Grafana SimpleJSON endpoints — most existing metric queries and panels work, with the documented divergences in Query Reference.
Simple operationsNo cluster to size, no JVM tuning, no separate archive tier. Backup is a file copy.
AI-nativeTelemetry is exposed to LLM tooling through MCP servers rather than bespoke integrations.

Prerequisites#

Parqtel has no external dependencies. What you need depends on how you run it.

DeploymentRequirement
Docker (recommended)Docker Engine 20.10+ on linux/amd64 or linux/arm64.
Homebrew (Linux & macOS)Homebrew on Linux or macOS (amd64 or arm64). No Rust toolchain needed.
From sourceRust 1.87 or newer.
KubernetesA cluster with Helm 3, and a PersistentVolume for the data directory.
StorageRoughly 1 GB of disk per 40–60 GB of raw telemetry, depending on signal mix and compression. See Performance & Scaling.
NetworkPort 8080 (HTTP API and console) and port 4317 (OTLP gRPC). Both are configurable.
↗

No authentication ships today. Parqtel has no built-in authentication or authorization. Run it on a trusted network or behind a reverse proxy that provides these. This is covered in full under Known limitations.

Getting started#

The fastest path from nothing to a queryable metric is about five minutes:

docker run -d --name parqtel \
  -p 8080:8080 -p 4317:4317 \
  -v parqtel_data:/data \
  ghcr.io/parqtel/parqtel-oss:0.3.1

curl http://localhost:8080/health

Then follow the Quickstart to send your first metric, log, and trace, and query them back.

Known limitations#

Parqtel is honest about what it does not do. The most important ones are summarised here; each links to the page that covers it in detail.

LimitationImpactDetails
No authentication or authorizationAnyone who can reach the port has full access. Use a trusted network or a reverse proxy.Troubleshooting
Instant queries see only the last 5 minutesA point older than the lookback window is invisible to an instant query; use a range query instead.Query Reference
Range queries skip the final partial stepA range query returns one fewer sample at the trailing edge than you may expect.Query Reference
Alerts cannot compare two metricsRules evaluate a single query, so ratios such as errors / requests are not expressible directly.Alerting
Recording rules and pipelines are not executedDefinitions are validated and stored through the API, but no scheduler or ingest-stage processor runs them in v0.3.1.How Parqtel Works
In-memory buffer is bounded only by RAMSustained throughput above your flush rate grows memory until the process is killed. Size it deliberately.Performance & Scaling
Log and trace scans read every columnLog and trace search is slower than metric queries on large datasets.Storage Model
