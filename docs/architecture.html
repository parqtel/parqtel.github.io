How Parqtel Works#

Parqtel is a single binary that accepts OpenTelemetry metrics, logs, and traces, makes them queryable immediately, and lands them in immutable Parquet blocks on ordinary storage. This page follows one request through that path end to end — transport, decode, buffer, derive, write-ahead log, flush, and commit — so you can predict where latency, memory, and durability come from.

Everything described here is observable from outside the process: through the HTTP API, the console at /ui, the self-metrics at /metrics, and the startup log. Contributor-level detail — which component owns which subsystem — lives in Internals & Contributor Notes.

The request path#

The seven stages are sequential for a given write, but the stages after the write-ahead log run off the request path. That is the single most useful thing to know about Parqtel's behaviour: acknowledgement is decoupled from block encoding, which is why a large batch does not make the client wait for a Parquet write.

Stage 1 — Transport#

Telemetry enters over HTTP or gRPC. Both transports run the same decode path, so a payload that is valid on one is valid on the other.

TransportAddressEndpointsNotes
OTLP over HTTPserver.bind_address, default 0.0.0.0:8080POST /v1/metrics, /v1/logs (content-negotiated: protobuf or JSON), plus /json variants. Traces use POST /v1/traces or /v1/traces/json, which accept JSON only today.gRPC is the preferred transport for traces; the HTTP trace path does not decode protobuf.
OTLP over gRPCserver.grpc_bind_address, default 0.0.0.0:4317All three OpenTelemetry collector services (metrics, logs, traces)The OpenTelemetry SDK default transport. Set the key to an empty string to disable the listener.

Both transports honour ingest.max_body_size (default 10485760, 10 MB). The gRPC message limits are derived from that same value rather than set separately, so the two transports cannot disagree about what a legal batch is — a batch that succeeds over HTTP also succeeds over gRPC.

A batch larger than storage.max_rows_per_block is split across blocks, not rejected. server.grpc_concurrency_limit (default 64) bounds concurrent exports per gRPC connection, so one busy client cannot monopolise the ingest queue that HTTP exporters share.

↗

No authentication ships today. Every ingest endpoint and the gRPC port are open, and CORS accepts any origin. Terminate TLS and authenticate in front of Parqtel — see Deploy.

Stage 2 — Decode#

The payload is converted into Parqtel's internal metric, log, and span shapes. For traces, resource attributes are merged into span attributes, and span attributes win on conflict — a span-level service.name overrides the resource-level one.

Decoding is CPU work and never occupies a request-handling thread that is also responsible for serving queries. Malformed payloads return 400 and are counted in parqtel_ingest_errors_total; a body over the limit returns 413.

Stage 3 — Live buffer#

Every decoded value enters an in-memory buffer before any file is written. That buffer is what makes a metric you sent one second ago queryable one second later, rather than after the block window closes.

SignalHow the buffer answers a query
MetricsIndexed by metric name; matched with the same label semantics as flushed data.
LogsScanned within the requested time window.
TracesMatched by interval overlap on the span's start and end time.

Two behaviours here are worth internalising:

  • service.name from the resource is injected into point labels. A PromQL matcher behaves identically against buffered and flushed data, so a query does not change its answer just because a flush happened in between.
  • The buffer drains only when a block becomes durable, never when a flush is merely scheduled. Buffered and flushed rows therefore never double-count, and a row is never in neither place.

The cost of this design is that the buffer has no size limit — see Known limitations.

Stage 4 — Derive & sample#

Two transformations happen after decode and before storage.

Derived RED metrics. Every server-kind span automatically produces traces_service_requests_total, traces_service_errors_total, and traces_service_duration_ms, labelled by service, operation, and service.name. These flow back through the normal metrics path, so a service gets request/error/duration dashboards without hand-written instrumentation.

The bridge emits one gauge sample per server span: requests is 1, errors is 1 or 0, and duration is the span duration in milliseconds. Despite the _total suffix, these are not cumulative counters in v0.3.1, so build rates and averages with count_over_time, sum_over_time, and avg_over_time rather than rate(). See Automatically derived RED metrics.

Tail sampling. A trace is kept if any rule votes keep, evaluated in order:

Sampling runs after RED derivation, so dropping a healthy trace never depresses your derived metric rates. The decision is a deterministic hash of the trace ID, so every span of a trace reaches the same verdict — traces live or die whole. Per-service policies fully replace the global policy for that service.

KeyDefaultEffect
ingest.tail_sampling.keep_errorstrueKeep traces containing ERROR-status spans.
ingest.tail_sampling.slow_trace_msunsetKeep traces whose server spans exceed this duration. Unset disables the rule.
ingest.tail_sampling.sampling_ratio1.0Fraction of the remaining traces to keep (validated to 0.0–1.0).

The default keeps everything at zero cost. See Ingest Telemetry for worked policies.

Stage 5 — Write-ahead log, then acknowledge#

Each decoded value is appended to its signal's write-ahead log, and the HTTP request is acknowledged once that append returns — not once a Parquet file exists. With the defaults, the crash-loss window is one sync interval (1 second) rather than a whole block window (2 hours for metrics).

The append happens under the same lock that orders the writer, so log order and writer order are one total order. That is the property that makes the commit point meaningful. The full protocol, the on-disk working set, and the settings are on Durability & Recovery.

SignalWAL enabled byDefault
Metricsingest.wal_enabledtrue
Tracesingest.wal_enabledtrue
Logsingest.log_wal_enabledtrue

A WAL that cannot be opened fails startup. Continuing would mean accepting data Parqtel cannot promise to recover.

Stage 6 — Rotate & flush#

A block is closed when either trigger fires:

TriggerKeyDefault
Timestorage.block_duration_secs (metrics and traces)7200 (2 h)
Timelogs.block_duration_secs1800 (30 min)
Rowsstorage.max_rows_per_block1000000
Rowslogs.max_rows_per_block200000

server.flush_interval_secs (default 5) is the background tick that checks whether a duration-triggered block is due. It bounds how late such a flush can be — a block flushed up to 5 seconds after its window closes is normal — not how often blocks are written.

The row cap is checked before a batch is pushed, so a batch larger than the cap is split across blocks instead of being half-rejected.

Metrics with a WAL attached encode on a background flush worker bounded by ingest.max_inflight_flushes (default 4). A full queue encodes inline, so backpressure degrades to synchronous rather than growing an unbounded backlog. Logs and traces always encode inline.

⚠

Background flushing requires a WAL. With ingest.wal_enabled = false, the worker refuses to start and metrics flushing stays synchronous — a request is never acknowledged before its data is recoverable.

Stage 7 — Publish & commit#

The block becomes real in a fixed order. Each step exists to make one crash point safe.

Three rules carry the guarantees:

  • Rename before publish. A block becomes visible atomically. There is no window in which a half-written file is queryable.
  • The commit point advances only after the block is renamed into place and the index sidecar is durable. Advancing it earlier is the one failure a WAL exists to prevent.
  • The memory buffer drains last. Draining earlier would leave rows in neither the buffer nor a block — invisible to every query until the encode landed.

If the index sidecar does not become durable, Parqtel logs the timeout and does not commit, leaving the rows in the WAL for replay. The cost is a duplicate row after restart, which the commit-point skip collapses; the alternative would be data loss.

The query path#

All three query surfaces read the buffer and the blocks through one engine.

SurfaceSignalsGrammarEndpoint
ParQLMetricsPromQL-compatible: selectors, functions, aggregations with by / without, binary operators with on() / ignoring() / group_left, subqueries, offsetGET /api/v1/query, GET /api/v1/query_range
ParqtelQLLogs, tracesLenient boolean search: terms, phrases, wildcards, -exclusion, OR/AND/NOT, field operators, ranges, field:* exists, body: contains, severity thresholdsGET /api/v1/logs, GET /v1/traces/search
PQL pipelinesAll three`fetch … \filter … \

A query resolves in three stages, cheapest first — index lookup by time range and metric-name membership, then row-group and column pruning, then decode and evaluate. The pruning chain is detailed on Storage Model; the grammar and result limits are on Query Reference.

Two user-visible behaviours come from the query engine rather than the storage layer:

  • Instant queries look back 5 minutes (query.lookback_delta_ns, default 300000000000 — the Prometheus default). Data older than that is on disk but outside an instant query's window.
  • A range query does not evaluate its final partial step. Steps run while ts < end, so the last instant evaluated is up to one step before end.

Query evaluation runs off the request-handling threads, so a wide range query cannot stall ingest. Result limits (query.max_series default 1000, query.max_samples_per_series default 10000) truncate silently — compare totalSeriesCount against the series you received to detect it.

The alert path#

Rules are YAML documents under alerts.rules_dir (default rules), loaded non-recursively at startup. There is no file watcher: edit files and restart, or use the rules API (POST/PUT/DELETE /api/v1/rules) to change rules without a restart. Each enabled rule is evaluated every server.alert_interval_secs (default 15) over a trailing query.lookback_delta_ns window. In v0.3.1 the evaluator thresholds the newest raw sample of each matching series; it does not apply rate(), aggregations, or histogram_quantile(). An alert therefore does not necessarily match a dashboard expression built on the same window.

Each alert instance moves through Inactive → Pending → Firing → Resolved. Instances are persisted with their transition history and are visible at GET /api/v1/alerts and in the alert stream in the console.

Rule queries should be bare metric selectors. See Known limitations for what that excludes.

Two settings are accepted but do not yet change runtime behaviour in v0.3.1: alerts.refinement_enabled and the [alerts.postmortem] block. The alerts.noise_window_firings / alerts.noise_suppression_threshold knobs are likewise reserved — instances are stored with a noise_score of 0 and no scoring pass runs. Treat them as forward-looking configuration, not controls.

The pipeline path#

The pipeline and recording-rule APIs accept definitions today, but the shipped server does not execute them yet: no ruler scheduler or ingest-stage processor is wired into the running process in v0.3.1.

  • Recording rules (POST /api/v1/recording_rules) are validated and stored; they do not evaluate on a schedule or write derived metrics.
  • Stream pipelines (POST /api/v1/pipelines) are validated and stored; they do not transform ingested data or extract metrics.

The definitions are managed over the API and are the seam a future release will run:

MethodEndpoint
GET/api/v1/pipelines
POST/api/v1/pipelines
DELETE/api/v1/pipelines/{name}
GET/api/v1/recording_rules
POST/api/v1/recording_rules

Do not build on derived series yet; write the alert rule or dashboard against the raw signal instead.

The console#

The web console ships inside the same binary at /ui — no separate install, no external requests, and it works air-gapped. / redirects to it.

ViewWhat it does
OverviewPer-signal stat cards, storage and ingest-volume charts, and live ingestion-rate cards backed by GET /api/v1/ingest_rates.
Query builderFunction catalogue with typed argument editors, by / without grouping, live preview, and bounded high-cardinality autocomplete that never enumerates a high-cardinality label.
LogsFacet sidebar and full-text search over log bodies.
TracesBrowse grouped by trace, with a waterfall view.
AlertsThe alert stream, an evidence tab pairing the metric chart with correlated logs, and a form-based rule editor.

Configuration layering#

Settings resolve from four sources, highest priority first.

PrioritySourceExample
1CLI flags--config, --bind, --data-dir, --log-level
2Environment variablesPARQTEL__STORAGE__COMPRESSION — PARQTEL__ prefix, __ as the nested separator. The single-underscore form also works.
3TOML config fileconfig/default.toml, or the path from --config / PARQTEL_CONFIG
4Built-in defaultsEverything documented on the Configuration page.

Every value is validated at startup, including combinations that would silently disable an optimisation — a storage.row_group_size above storage.max_rows_per_block is rejected with a message naming both keys, rather than accepted and left to cost you query time.

Known limitations#

LimitationImpactWorkaround
The in-memory buffer is unboundedResident memory grows with ingest rate × block duration until a flush happens. A rate that fits at 100 k points/s can OOM at 300 k. The WAL does not help — it bounds crash loss, not memory.Lower storage.block_duration_secs; watch parqtel_process_rss_bytes; size the container from the sizing formula.
No authentication or authorizationEvery endpoint, including ingest and gRPC, is open; CORS accepts any origin. The console carries the same privileges as the API.Do not expose 8080 or 4317 publicly. Terminate TLS and authenticate at a reverse proxy or service mesh.
Alert rules evaluate raw samples onlyIn v0.3.1 the alert loop builds its query plan without a step, so rate(), increase(), aggregations, and histogram_quantile are parsed but not applied. Composed queries such as sum(rate(...)) can silently match no series.Alert on a gauge whose current value is the signal you care about, or precompute rates/ratios before ingestion. See Alerting.
Log and trace scans decode every columnWide log and trace queries are slower and cost more memory than the equivalent metric query.Narrow the time window and pre-filter with index-backed selectors rather than scanning everything.
Instant queries see only the last 5 minutesA point older than the lookback window is invisible to /api/v1/query.Use /api/v1/query_range, or raise query.lookback_delta_ns (which also widens what alerts can see, and costs memory).
A range query skips its final partial step/api/v1/query_range over [now-300, now] with step=60 returns nothing for the most recent minute.Use step <= 15, or end the window at now - step. This matches Prometheus.
Background flushing requires the WALWith ingest.wal_enabled = false the flush worker never starts and requests wait on the synchronous encode.Keep ingest.wal_enabled = true in any deployment where ingest latency matters.
Result limits truncate silentlyExceeding query.max_series or query.max_samples_per_series returns a shorter response with no error and no status code.Compare totalSeriesCount against the series you received.
