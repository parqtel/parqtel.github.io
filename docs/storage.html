Storage Engine

Parqtel stores data in self-contained, immutable Parquet block files. Blocks are never modified in place, so a query is a set of prune decisions followed by a parallel read — and a backup is a file copy.

↗

Implementation: parqtel-core/src/storage/ — scanner.rs, index.rs, compactor.rs, retention.rs, persist.rs. Schemas are canonical in models/storage/schema.rs.

Block naming

SignalPattern
Metrics{start_ns}_{end_ns}_{uuid}.parquet
Logslogs_{start_ns}_{end_ns}_{uuid}.parquet
Tracestraces_{start_ns}_{end_ns}_{uuid}.parquet

Timestamps are nanoseconds since the epoch; uuid is 32 lowercase hex characters. Every writer writes to .tmp_{filename} then fs::renames into place, so a block becomes visible atomically. Sidecars use index.tmp → rename.

⚠

Trace blocks live in the metrics directory. TraceWriter is built from storage.*, so trace .parquet files sit alongside metric blocks; only the trace index is one level down in data/traces/. Backing up data/ therefore captures both metric and trace blocks.

Config validation rejects row_group_size of 0, or above max_rows_per_block. Either combination silently disables row-group pruning — a performance regression, not a correctness one, which is exactly why it is treated as an error.

Parquet schemas

Defined canonically in parqtel-core/src/models/storage/schema.rs, written with the arrow/parquet 59 stack at WriterVersion::PARQUET_2_0. All three schemas are flat (no nested groups), which is what lets the scanner project by leaf index safely.

Metrics — 15 columns

ColumnTypeRole

At write time extract_correlation_labels lifts service.name, service.version and the k8s.* keys out of resource attributes into their own dictionary columns — fast equality filtering. Only the dotted OTLP keys are recognised; service_name is not an alias.

Logs — 19 columns

timestamp_ns, observed_timestamp_ns, severity_number (Int32), severity_text, body, the seven correlation columns, trace_id (16 bytes), span_id (8 bytes), flags, scope_name, scope_version, attributes (JSON) and resource_attributes (JSON).

Traces — 24 columns

timestamp_ns, span_id, span_name, span_kind, start_time_ns, end_time_ns, duration_ns, status_code, status_message, the seven correlation columns, trace_id, parent_span_id, flags, trace_state, attributes, resource_attributes, events and links.

Signal detection during reconciliation reads the schema, not the filename: severity_text → Logs, then metric_kind → Metrics, then start_time_ns → Traces. The order matters because log blocks also carry a span_id column.

Per-column encoding is not configured — Parquet dictionary-encodes string columns by default. A proposed Arrow-level series dictionary for the labels column was measured at 0 % benefit (810 614 B vs 810 678 B) and dropped: the premise was false, because the encoding it would add already exists.

The pruning chain

Every metrics query walks five levels, cheapest first. Each level can only skip work it can prove is unnecessary.

query
  │
  ├─ ① BlockIndex::query          in-memory Vec, binary search      no I/O
  │     time window + metric-name set membership
  │
  ├─ ② row_groups_in_range        Statistics::Int64 on timestamp_ns
  │     min/max overlap, null-count guard
  │
  ├─ ③ row_groups_matching_value  Statistics::ByteArray on metric_name
  │     min/max first (exact, free) → bloom filter only as fallback
  │
  ├─ ④ row_groups_matching_value  same two-tier test on service_name
  │     only when the query has a service.name *equality* matcher
  │
  ├─ ⑤ ProjectionMask::leaves     7 of 15 metrics columns
  │
  └─ spawn_blocking × 16          ≤ 128 blocks; row filters before allocation
↗

The chain fails open. Missing statistics, a missing bloom filter, an absent column or an unevaluable condition all keep the row group. A false positive costs one extra block read; a false negative would be data loss. The worst case is always the behaviour that existed before any of this.

Why statistics beat bloom

Rows are written grouped by (metric_name, metric_kind, resource_attributes), so a row group's metric_name and service_name min and max are usually the same value. Testing the needle against that range is exact and free — no filter read, no probabilistic answer. Bloom filters are consulted only when statistics cannot decide (column missing, no min/max, unexpected physical type), where a false positive is possible.

One nuance: the name test is one-sided. min/max cover non-null values only, so unlike the time prune it needs no null-count guard — a null row cannot contain the value being searched for.

Column projection

The metrics scan reads 7 of 15 columns. The list is a module constant, not computed per query:

const METRIC_SCAN_COLUMNS: [&str; 7] = [
    "timestamp_ns", "metric_name", "service_name", "labels",
    "value_float", "value_int", "value_complex",
];

Skipped: metric_kind, service_version, the five k8s_* dictionaries and resource_attributes.

  • The projection is intersected with the file's own schema before being applied, so blocks from older builds stay readable.
  • The decoder resolves every column index by name from the batch's own schema, because a projection renumbers positions. Hard-coded positions against a projection is exactly how a projection silently starts reading the wrong column — the regression test is adversarial because labels and value_complex are both Utf8, so swapping them type-checks and returns wrong data.

Logs and traces are not projected. Open work: events, links and the k8s_* dictionaries are likewise unused by those decoders. See known issues.

Block index

BlockIndex holds a Vec<BlockMetadata> kept sorted by start_timestamp_ns after every mutation — query binary-searches on that invariant. It performs no filesystem I/O of its own; persistence belongs to BlockIndexStore.

Sidecar format

index.json, one per signal, a bare JSON array of BlockMetadata (no envelope, no version field), written tmp+rename:

[{ "path": "…", "start_timestamp_ns": …, "end_timestamp_ns": …,
   "row_count": …, "size_bytes": …,
   "metric_names": {…}, "label_names": {…},
   "label_values": { "field": ["v1", …] },
   "signal_type": "Metrics" }, …]

Writes are batched: mutations set a dirty flag and one persist_once runs per server.index_persist_interval_secs (default 2 s). It serialises under a read lock and writes on the blocking pool with no lock held; a mutation landing mid-pass simply re-sets the flag. Compaction and retention call mark_dirty() and never write the sidecar themselves.

metric_names~50055 %

metric_names dominates because the same name is stored once per block. A per-block bloom filter over names (~10 bits/name) would cut ~55 % of a sidecar that is itself 23 % of storage ⇒ ~13 % of total storage. It is sound (a false positive costs one extra block read, never a missing result) but is a sidecar format change needing a read-old/write-new story, so it is deliberately not built. Watch it live as parqtel_index_sidecar_bytes{signal=…}.

Label-value index

At flush time each block records a per-field distinct-value dictionary (label_values), capped at 10 000 values per field. /api/v1/label/<name>/values reads it from metadata instead of decoding blocks — the executor layers the in-memory buffer over the newest blocks' dictionaries, bounded to the last 5 blocks, and the API clamps limit to 100. On a 100 000-value user_id that is ~1.2 µs and 10 values per keystroke versus ~15.6 ms and 100 000 values for a full enumeration.

Compaction unions the source dictionaries under the same cap into the merged block. Before that fix, every compaction pass replaced N dictionaries with one empty one, degrading autocomplete on every pass until the source blocks aged out.

Reconciliation

At startup the index is reconciled against the data directory in both directions — see durability & recovery for the full procedure and its caveat.

Compaction

Runs every compaction_interval_secs (default 3600 s, floored at 60 s) in two passes.

Pass A — small-block merge

  • Trigger: ≥ 2 blocks with row_count < 10 000.
  • Selection: in index order, truncated to compaction_max_merge_blocks (default 12, floored at 2).
  • Execution: spawn_blocking with no lock held — decode, union dictionaries, write merged.
  • Publication: one replace() under a write lock plus mark_dirty() — no I/O, sidecar deferred.
  • Deletion last: sources are removed only after the merge is published, so a crash in between leaves redundant blocks (harmless) rather than a dangling index entry (a query error).

Pass B — tiered warm/cold

  • Candidates: same signal, older than 6 h, and under 500 000 rows (do not re-merge already-large blocks).
  • Tier window: 24 h if any candidate is older than 24 h, else 6 h.
  • Greedy adjacent grouping from an anchor; singleton groups skipped; groups truncated to compaction_max_merge_blocks.
  • Budget: compaction_max_merges_per_pass (default 8) across the whole cycle. One merge per signal per hour cannot keep up with a cluster whose small blocks arrive faster than that.
⚠

Traces are not compacted by the shipped server. The compactor now handles trace blocks — the code path is implemented and unit-tested (3 small trace blocks merge to 1, all spans survive, the merged block still decodes) — but main.rs only starts maintenance for metrics and logs. Traces get retention and index persistence, not compaction. If you rely on trace compaction today, metrics and logs are the affected ones, and trace blocks will continue to accumulate until retention deletes them.

Retention

Runs every server.retention_interval_secs (default 3600 s), shared across all three signals:

  1. cutoff = now − retention_days
  2. Select expired blocks under a read lock — taking the write lock would block every query handler for the whole deletion batch
  3. Empty ⇒ return immediately without creating the sidecar — a read-only deployment leaves no stray file and pays no write
  4. Unlink each path on the blocking pool; NotFound ignored, anything else logged and counted
  5. Drop the index entries and mark dirty
↗

An index entry is dropped only for a file that was actually expired and removed. Orphaning a live file would hide its data from queries forever, with nothing on disk left to rebuild from.

Configuration

Storage configuration is flat — there is no blocks.metrics.* nesting. Traces reuse [storage] entirely.

[logs] has the same shape minus backend, with defaults data_dir="data/logs", block_duration_secs=1800, max_rows_per_block=200000, row_group_size=20000, retention_days=3. Its validation delegates to the same shared rule set, so the two blocks cannot drift apart.

Compile-time constants, not configuration

MAX_BLOCKS = 128 · MAX_CONCURRENT = 16 · LABEL_CACHE_MAX = 10 000 · BLOOM_FPP = 0.01 · COLUMN_INDEX_TRUNCATE_LENGTH = 64 · DATA_PAGE_SIZE_LIMIT = 512 KiB · MAX_ZSTD_LEVEL = 22 · compaction thresholds 10 000 rows and 500 000 rows · tier windows 6 h / 24 h.

Backup and portability

  • Blocks are immutable. Copy or snapshot the data directory while the server runs.
  • The sidecar is a cache, never the source of truth. Back it up for fast startup, but a lost or stale index.json repairs itself at startup via reconciliation.
  • Rolling back is safe. Blocks are self-describing Parquet and the previous binary reads them. Rolling forward across the arrow2 → arrow 59 migration is not — that encoding change needs a data-directory wipe.
