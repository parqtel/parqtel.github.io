Internals

Storage Model#

Parqtel stores every signal as self-contained, immutable Parquet block files. Blocks are never modified in place, so a query is a set of prune decisions followed by a parallel read — and a backup is a file copy.

This page covers what a block contains, how blocks are named and laid out, the order in which a query discards work, and how compaction and retention keep the directory healthy. Durability of the write is on Durability & Recovery; the measured cost of these decisions is on Performance & Scaling.

The block lifecycle#

A block is written once and never edited. That single property is what makes concurrent queries safe without locks, makes a backup a file copy, and makes rolling back to a previous Parqtel version safe within the same on-disk format.

On-disk layout#

LocationHolds
storage.data_dir (default data)Metric blocks, trace blocks, the metrics sidecar, the traces sidecar directory, and the metrics and traces write-ahead logs.
logs.data_dir (default data/logs)Log blocks, the logs sidecar, and the logs write-ahead log.
↗

Trace blocks live in the metrics directory. Traces reuse the whole [storage] section, so trace .parquet files sit alongside metric blocks; only the trace index lives one level down. Backing up storage.data_dir therefore captures both metric and trace blocks.

Block naming#

SignalPattern
Metrics{start_ns}_{end_ns}_{uuid}.parquet
Logslogs_{start_ns}_{end_ns}_{uuid}.parquet
Tracestraces_{start_ns}_{end_ns}_{uuid}.parquet

Timestamps are nanoseconds since the Unix epoch; the UUID is 32 lowercase hex characters. Every block is first written under a temporary name and then renamed into place, so a block becomes visible atomically — a query never sees a partially written file. Sidecars use the same technique.

Block parameters#

storage.compression accepts zstd, snappy, lz4, or none. storage.compression_level applies to zstd only (1–22) and is rejected, not ignored, for the other codecs — a setting that silently does nothing is worse than a startup error.

Validation rejects a row_group_size of 0 or one above max_rows_per_block. Either combination disables row-group pruning, which is a performance regression with no visible error — which is exactly why it fails startup instead.

What a block contains#

All three schemas are flat — no nested groups — which is what lets a query read only the columns it needs.

Metrics#

Column groupContentsRole
timestamp_nsSample timeTime pruning
metric_nameMetric nameName pruning
metric_kindCounter, gauge, histogram, summary—
service_nameService the sample belongs toService pruning; merged back as the service.name label on read
service_versionService versionCorrelation
k8s_namespace, k8s_pod_name, k8s_pod_uid, k8s_container_name, k8s_node_nameKubernetes identityCorrelation (nullable)

At write time, service.name, service.version, and the k8s.* keys are lifted out of the resource attributes into their own dictionary columns for fast equality filtering. Only the dotted OpenTelemetry keys are recognised — service_name is not an alias, and a resource attribute spelled that way stays inside resource_attributes.

Logs and traces#

Log blocks carry the log body, severity, timestamps, trace and span IDs, scope information, and both attribute sets. Trace blocks carry the span identity and kind, start/end/duration, status, parent span, and span events and links, alongside the same correlation columns as metrics.

When Parqtel reconciles a block it does not know, it reads the schema, not the filename: a block with a severity column is logs, one with a metric kind is metrics, one with a start time is traces. The order matters, because log blocks also carry a span ID. A misnamed file can therefore cause a block to be missed — never to be wrongly adopted as another signal.

The pruning chain#

Every metrics query walks the same five levels, cheapest first. Each level can only skip work it can prove is unnecessary.

LevelWhat it usesApplies to
1 · Block indexBlock start/end times and the block's metric-name set, held in memoryMetrics, logs, traces (metrics and logs additionally test name membership)
2 · Time rangeMin/max statistics on the timestamp columnMetrics, logs, traces
3 · Metric nameMin/max statistics on metric_name, with the bloom filter as fallbackMetrics
4 · Service nameThe same two-tier test on service_name — only for an equality matcherMetrics (opt-in, since it depends on the query shape)
5 · Column projectionReading 7 of the 15 metrics columnsMetrics only

Why it fails open#

Every level fails open. Missing statistics, a missing bloom filter, an absent column, or a condition the reader cannot evaluate all keep the row group. A false positive costs one extra block read; a false negative would be data loss. The worst case is always the behaviour that existed before any pruning.

Why statistics beat bloom filters#

Rows are written grouped by metric name, so a row group's metric_name and service_name minimum and maximum are usually the same value. Testing a name against that range is exact and free — no filter to read, no probabilistic answer. Bloom filters are consulted only when statistics cannot decide, such as a truncated column index or an unexpected physical type.

One nuance: unlike the time test, the name test is one-sided. The statistics cover non-null values only, and a null row cannot contain the name you are searching for, so no null-count guard is needed.

Column projection#

The metrics scan reads 7 of 15 columns: the timestamp, the metric name, the service name, the point labels, and the three value columns. Skipped: metric_kind, service_version, the five k8s_* dictionaries, and resource_attributes.

Logs and traces are not projected. Their scans decode every column, which is why a wide log or trace query is slower and costs more memory than the equivalent metric query. Narrowing the time window is the effective workaround.

The block index#

The block index is the metadata that lets a query skip work before touching disk. It is kept in memory, sorted by block start time, and persisted to one index.json per signal, written beside the blocks.

Each entry records the block's path, start and end timestamps, row count, size, metric names, label names, and a per-field set of label values.

Label-value autocomplete#

At flush time each block records a per-field dictionary of distinct label values, capped at 10 000 values per field. GET /api/v1/label/{name}/values answers from that metadata instead of decoding blocks, layering the in-memory buffer over the newest blocks' dictionaries and clamping limit to 100.

The practical effect on a 100 000-value user_id: a bounded top-10 lookup costs about 1.2 µs and returns 10 values per keystroke, against roughly 15.6 ms and 100 000 values for a full enumeration. Compaction unions the source dictionaries into the merged block under the same cap, so autocomplete does not degrade as blocks are merged.

Index size#

The sidecar is real storage, not free metadata.

MeasureObserved
Data described35.6 MB across 1 226 blocks (~29 KB per block)
index.json8.20 MB (~6.7 KB per block)
RatioThe sidecar is about 23 % of the data it describes
GrowthLinear in block count — roughly 0.3 GB per day at ~32 blocks/minute
Bounded by retention?No. Expired blocks drop their entries, but the index grows with block creation rate, not with retained data volume.

Roughly 55 % of each sidecar is the metric-name set, because the same name is stored once per block. A per-block bloom filter over names would cut about 13 % of total storage — it is a sound change but a sidecar format change, so it is deliberately not built. Watch the live figure with parqtel_index_sidecar_bytes{signal=…}.

Lowering storage.max_rows_per_block or shortening the block duration increases block count, and therefore index size, proportionally. If you tune either key for memory reasons, watch parqtel_index_sidecar_bytes afterwards.

Reconciliation — the self-healing index#

At startup the index is reconciled against the data directory in both directions:

DirectionAction
AdoptBlock files the index has never seen are recovered from their Parquet footer and added.
DropIndex entries whose file has gone are removed.

When anything was repaired you get one warning per signal naming how many blocks were adopted, dropped, and found unreadable.

This makes the sidecar a cache, never the source of truth. Back it up for fast startup, but a lost or stale index.json repairs itself.

↗

A recovered block has no name index. It carries an empty metric-name set, which means unknown — not matches nothing. The block stays visible to every query, but name-based pruning does not apply to it, and label-value autocomplete stays empty for it, until compaction rewrites the block with a full flush-time index.

↗

Trace reconciliation cannot adopt its own blocks. Trace blocks sit in the parent data directory while the trace sidecar lives in the traces/ subdirectory, so the scan does not see them. A lost trace index is rebuilt from WAL replay and normal flushing, not by adoption.

Compaction#

Compaction runs every storage.compaction_interval_secs (default 3600, floored at 60 s) in two passes. Its purpose is to cut file count and query fan-out by merging small blocks into larger ones.

PassTriggerSelectionBudget
A — small-block mergeTwo or more blocks with fewer than 10 000 rowsIn index order, truncated to storage.compaction_max_merge_blocks (default 12, floored at 2)—
B — tiered warm/coldSame signal, older than 6 hours, under 500 000 rowsGreedy adjacent grouping from an anchor within a 24-hour window (6 hours if no candidate is older than 24 hours); singleton groups skippedstorage.compaction_max_merges_per_pass (default 8) across the whole cycle

Two safety rules apply to both passes:

  • Deletion happens last. Sources are removed only after the merged block is published, so a crash in between leaves redundant blocks — harmless — rather than a dangling index entry, which would be a query error.
  • Compaction does not re-merge large blocks. Pass B skips blocks at or above 500 000 rows.
↗

Traces are not compacted by the shipped server. Trace blocks receive retention and index persistence but no compaction, so they accumulate until retention deletes them. If you rely on trace compaction today, expect a higher file count and slower wide trace scans than metrics of the same volume. Work around it by shortening storage.retention_days for traces or by keeping trace queries narrow; metrics and logs are unaffected.

Retention#

Retention runs every server.retention_interval_secs (default 3600, shared across all three signals). For each signal, blocks whose window ended before now − retention_days are deleted.

KeyDefaultApplies to
storage.retention_days7Metrics and traces
logs.retention_days3Logs

Selection happens under a read lock — taking the write lock would block every query handler for the whole deletion batch — and unlink happens off-lock. A deletion sweep therefore never blocks a query. When nothing is expired the sweep returns without writing anything, so a read-only deployment leaves no stray file and pays no write.

An index entry is dropped only for a file that was actually expired and removed. Orphaning a live file would hide its data from queries forever, with nothing on disk left to rebuild from.

↗

The block index is not bounded by retention. Retention deletes blocks and their entries, but index size tracks how many blocks you created, not how much you keep. A short block duration with a short retention still produces a large sidecar.

Backup and portability#

PropertyWhat it means for you
Blocks are immutableCopy or snapshot storage.data_dir and logs.data_dir while the server runs. No quiesce step is required.
The sidecar is a cacheBack up index.json for fast startup, but a lost or stale one repairs itself at startup.
WAL segments are not backupsThey are an in-flight buffer. A replay reconstructs unflushed rows, it does not archive flushed ones.
Rolling back is safeBlocks are self-describing Parquet and the previous binary reads them.
Rolling forward across the encoding migration is notBlocks written before the on-disk encoding change are unreadable by current builds. Crossing that boundary requires wiping the data directory. See Release Notes.

See Back Up & Upgrade for procedures.
