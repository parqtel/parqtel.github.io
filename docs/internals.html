Internals & Contributor Notes#

This page holds implementation detail that was removed from the end-user documentation. It is reference material for people working on Parqtel, not documentation of how to use it.

If you are operating Parqtel, you do not need anything on this page. Start at the Overview instead.

Why this content moved here#

The end-user docs previously named source files, internal crates, and specific library versions inline. That made the docs hard to read for anyone who had not already read the code, and it coupled the prose to file layout that changes independently of behaviour.

Behavioural guarantees that users depend on — compression results, durability bounds, query semantics — remain in the user-facing pages. The implementation of those guarantees lives here.

Component layout#

Parqtel is a Cargo workspace of 14 crates. Everything other than the MCP sidecars depends only on the shared core crate.

parqtel-server ─┬─ parqtel-core
                ├─ parqtel-ingest  ─┐
                ├─ parqtel-query   ─┼─ parqtel-core
                ├─ parqtel-alert   ─┤
                └─ parqtel-pipeline┘

parqtel-mcp-{slack,pagerduty,jira,notion,discord,gdocs,parqtel}
└── parqtel-mcp-core          # no dependency on parqtel-core
CrateResponsibility
parqtel-coreData models, storage engine, block index, scanner, compaction, retention, write-ahead log, configuration.
parqtel-ingestOTLP protobuf/JSON decoding, block rotation, WAL append, crash-safe Parquet writing, tail sampling.
parqtel-queryPromQL-compatible execution, ParqtelQL log/trace search, label matching, aggregations.
parqtel-alertRule registry, threshold evaluation, alert state machine, alert store, notification routing. (Noise scoring, refinement, and postmortem are scaffolded but not wired.)
parqtel-pipelineRecording-rule and stream-pipeline schemas, expression evaluation, and a ruler scheduler. The schemas are exposed over the API, but the scheduler and ingest processors are not started by parqtel-server in v0.3.1.
parqtel-serverHTTP server, route handlers, middleware, OTLP gRPC, self-telemetry, built-in UI. Produces the parqtel binary.
parqtel-mcp-coreShared MCP framework: Streamable HTTP transport, JSON-RPC, rate limiting, tool registry, parameter sanitisation.
parqtel-mcp-{slack,pagerduty,jira,notion,discord,gdocs,parqtel}Standalone tool servers for external integrations and for querying Parqtel itself.

OpenAPI spec accuracy#

The published OpenAPI specification is not authoritative. It is generated alongside the code and is known to diverge from the running server in places. Treat the HTTP API Reference and the live server as the source of truth, and verify against a running instance when in doubt.

This caveat was previously stated inside the end-user API page, where it read as a defect rather than a contributor note. It is recorded here instead.

Code conventions#

  • Safety: unsafe is forbidden workspace-wide.
  • Errors: every fallible path returns a typed error; no panics on request paths.
  • Release profile: optimised for throughput with crash-safe writes enabled.

Scaffolded but not wired#

Several subsystems exist in the workspace as typed, validated code but are not started by the parqtel binary in v0.3.1. This is intentional and documented in the user-facing pages, but it is easy to misread the code as active:

SubsystemState
Recording rules (parqtel-pipeline::ruler)Schema and scheduler exist; parqtel-server never constructs a RulerScheduler, so no group evaluates.
Stream pipelines (parqtel-pipeline::pipeline)Schema and registry exist; ingest never consults pipeline_registry.
Noise scoringnoise_score is carried on instances but always 0; no scoring pass runs.
Alert refinement (alerts.refinement_enabled)Config parsed; no refinement pass.
Postmortem automation ([alerts.postmortem])Config parsed; no engine wired.
CLI compactrun_compact only logs and returns Ok(()); background compaction still runs inside serve.

One wired-but-limited path is worth calling out for contributors: alert evaluation runs in parqtel-server/src/main.rs, not in parqtel-alert::EvaluationEngine (whose evaluate_rule is a stub). The server loop builds a QueryPlan with step_ns = None, so range functions and aggregations are parsed but not applied; it thresholds the newest raw sample. See Alerting.

When adding one of these, wire it in parqtel-server/src/state.rs / main.rs and update the corresponding user-facing page in the same change.

Build, test, and release#

cargo build --release          # the `parqtel` binary
cargo test --workspace         # unit + integration tests
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check

The Makefile wraps the common workflows: make dev-setup copies .env.example → .env and brings up the Compose stack; make local-up starts Parqtel, Grafana, Prometheus, and a load generator and waits for health; make test-api, make test-aggregations, and make test-functions exercise the HTTP surface against that stack.

Releases are cut from a tag on main; the release workflow builds the multi-arch image (published to GHCR) and the Helm chart (published as an OCI artifact). Chart version/appVersion track the workspace version.

For the full contributor process, see CONTRIBUTING.md; for vulnerability reporting, see SECURITY.md.
