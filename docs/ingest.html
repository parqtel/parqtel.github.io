Ingest Telemetry#

Parqtel accepts standard OpenTelemetry Protocol (OTLP) traffic, so you can point an existing SDK or Collector at it without writing a custom exporter. This guide covers connecting your sources, controlling what gets stored, and deriving useful signals automatically from raw spans and logs.

How ingestion works#

Three properties are worth knowing up front:

  1. Input is standard OTLP. Both gRPC and HTTP are accepted, with protobuf or JSON encoding over HTTP.
  2. Writes are acknowledged once durable. A request is answered after the record reaches the write-ahead log, not after the Parquet file is written. See Durability & Recovery.
  3. Data is queryable immediately. Newly ingested data is served from an in-memory buffer while it waits to be flushed.

Prerequisites#

RequirementDetail
Parqtel runningSee the Quickstart.
Network accessPort 8080 for HTTP ingestion, port 4317 for gRPC. Both configurable.
An OTLP-capable sourceAny OpenTelemetry SDK, the OpenTelemetry Collector, or plain curl.

Confirm intake is reachable before debugging your exporter:

curl http://localhost:8080/health

Choosing a transport#

TransportEndpointWhen to use
OTLP/gRPClocalhost:4317The default for OpenTelemetry SDKs across all three signals. Lowest overhead, supports streaming and compression.
OTLP/HTTP protobufPOST /v1/metrics, POST /v1/logsWhen gRPC is blocked by a firewall or proxy. Traces over HTTP do not accept protobuf.
OTLP/HTTP JSONPOST /v1/{metrics,logs,traces}/jsonDebugging, scripting, and quick tests. This is also the only HTTP path for traces (/v1/traces is JSON too).

All transports share the same decode path and the same size limit (ingest.max_body_size, default 10 MB), so a batch that succeeds on one transport will not fail on another.

Step 1 — Point an OpenTelemetry SDK at Parqtel#

Set the standard OTLP environment variables on your application. No code change is required.

gRPC (recommended):

export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4317"
export OTEL_EXPORTER_OTLP_PROTOCOL="grpc"
export OTEL_SERVICE_NAME="my-web-app"

HTTP protobuf:

export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:8080"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"
export OTEL_SERVICE_NAME="my-web-app"
↗

Traces over HTTP must be JSON. Parqtel's /v1/traces and /v1/traces/json endpoints accept JSON only, and no standard OpenTelemetry SDK ships an OTLP/HTTP-JSON trace exporter. For traces, use gRPC (:4317) directly or send them through an OpenTelemetry Collector that exports over gRPC.

Restart your application and confirm data arrives:

curl -s "http://localhost:8080/api/v1/query?query=up" | head

Recommended resource attributes#

Always set service.name. It is extracted into its own indexed column and is what the console groups by.

AttributeWhy it matters
service.nameIndexed; powers service-scoped filtering and the console.
service.versionIndexed; enables version-over-version comparison.
k8s.namespace.name, k8s.pod.name, k8s.pod.uid, k8s.container.name, k8s.node.nameExtracted into indexed columns for correlation.
↗

Note: only the exact dotted OTLP keys above are recognised. service_name is not an alias for service.name.

Step 2 — Point an OpenTelemetry Collector at Parqtel#

Add Parqtel as an exporter in your Collector configuration:

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 5s
    send_batch_size: 8192

exporters:
  otlp/parqtel:
    endpoint: parqtel.internal:4317
    tls:
      insecure: true

service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/parqtel]
    logs:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/parqtel]
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/parqtel]

Keep batches below ingest.max_body_size. If your Collector batches are larger, either reduce send_batch_size or raise the limit:

[ingest]
max_body_size = 20971520   # 20 MB

Step 3 — Send data directly (testing)#

A metric#

curl -X POST http://localhost:8080/v1/metrics/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceMetrics": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeMetrics": [{"metrics": [{
      "name": "http_requests_total",
      "sum": {"isMonotonic": true, "dataPoints": [{
        "asDouble": 1,
        "timeUnixNano": "'$(date +%s%N)'",
        "attributes": [
          {"key": "method", "value": {"stringValue": "GET"}}]}]}}]}]}]}'

A log record#

curl -X POST http://localhost:8080/v1/logs/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceLogs": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeLogs": [{"logRecords": [{
      "timeUnixNano": "'$(date +%s%N)'",
      "severityText": "INFO",
      "body": {"stringValue": "Checkout completed"},
      "attributes": [{"key": "user_id", "value": {"stringValue": "user_123"}}]}]}]}]}'

A span#

curl -X POST http://localhost:8080/v1/traces/json \
  -H "Content-Type: application/json" \
  -d '{
  "resourceSpans": [{
    "resource": {"attributes": [
      {"key": "service.name", "value": {"stringValue": "my-web-app"}}]},
    "scopeSpans": [{"spans": [{
      "traceId": "5b8efff798038103d269b633813fc60c",
      "spanId": "eee19b7ec3c1b174",
      "name": "GET /checkout",
      "kind": 2,
      "startTimeUnixNano": "'$(date +%s%N)'",
      "endTimeUnixNano": "'$(($(date +%s%N) + 42000000))'",
      "status": {"code": 1}}]}]}]}'
↗

OTLP/JSON attribute format. In OTLP/JSON, attributes must be an array of {"key": …, "value": {"stringValue": …}} objects. A plain JSON object map is rejected. This is the official OTLP JSON mapping and applies to all three signals.

Automatically derived RED metrics#

You do not need to instrument request rate, error rate, and duration separately. Parqtel derives them from server-kind spans as they are ingested.

For every service and operation, these metrics appear:

MetricMeaningLabels
traces_service_requests_totalOne gauge sample (1) per server spanservice, operation, service.name
traces_service_errors_totalOne gauge sample per server span: 1 if the span status is error, else 0service, operation, service.name
traces_service_duration_msSpan duration in milliseconds (one gauge sample per span)service, operation, service.name
↗

These are not cumulative counters. Despite the _total suffix on two of them, the bridge writes one gauge sample per span. rate() does not measure requests here, and rate(traces_service_requests_total[5m]) is effectively zero. Use count_over_time, sum_over_time, and avg_over_time.

Query them like any other metric:

curl --get "http://localhost:8080/api/v1/query" \
  --data-urlencode 'query=sum(count_over_time(traces_service_requests_total[5m]))'

Build a service dashboard from them:

# Requests per second by service (5-minute window)
sum by (service) (count_over_time(traces_service_requests_total[5m])) / 300

# Error count by service (5-minute window)
sum by (service) (sum_over_time(traces_service_errors_total[5m]))

# Error ratio
sum by (service) (sum_over_time(traces_service_errors_total[5m]))
  / sum by (service) (count_over_time(traces_service_requests_total[5m]))

# Average duration in milliseconds, weighted by span count
sum by (service) (sum_over_time(traces_service_duration_ms[5m]))
  / sum by (service) (count_over_time(traces_service_duration_ms[5m]))
↗

Important: RED metrics are derived before tail sampling runs, so your metric counts stay accurate even when only a fraction of traces is stored.

To derive RED metrics, the span must be server-kind ("kind": 2 in OTLP/JSON). Client and internal spans do not generate them.

Tail sampling#

Tail sampling decides whether to keep a trace after seeing the whole trace, so errors and slow requests survive while routine traffic is thinned out.

A trace is kept if any rule votes keep, evaluated in order:

  1. keep_errors — the trace contains an error-status span.
  2. slow_trace_ms — a server span exceeds the configured duration.
  3. sampling_ratio — a probabilistic decision hashed on trace_id.

Because the ratio is hashed on the trace identifier, whole traces live or die together — you never store half a trace.

[ingest.tail_sampling]
keep_errors = true
slow_trace_ms = 1000        # keep anything slower than 1s; unset disables
sampling_ratio = 1.0        # keep everything (default)

# Per-service override — fully replaces the global policy for that service
[ingest.tail_sampling.per_service.noisy-service]
keep_errors = false
sampling_ratio = 0.05
KeyTypeDefaultDescription
keep_errorsBooleantrueKeep traces containing error-status spans.
slow_trace_msIntegerunsetKeep traces with a server span slower than this. Unset disables the rule.
sampling_ratioFloat1.0Fraction of remaining traces to keep (0.0–1.0).
per_serviceTable{}Per-service overrides; each entry replaces the global policy for that service.

Choosing a ratio#

GoalSetting
Keep everything (default)sampling_ratio = 1.0
Reduce storage by ~90%, keep all errors and slow tracessampling_ratio = 0.1, keep_errors = true, slow_trace_ms = 1000
Tame one high-volume service onlyGlobal 1.0, plus a per_service block for that service

The default policy keeps everything at zero cost — the sampler is bypassed entirely.

Log-to-metric pipelines#

↗

Not executed in v0.3.1. The POST /api/v1/pipelines endpoint validates and stores pipeline definitions, and GET /api/v1/pipelines lists them, but no ingest-stage processor is wired into the running server yet. Defining a pipeline does not produce derived metrics today. Use an OpenTelemetry Collector processor/connector until this ships.

A pipeline definition has a name, an optional match block, and a list of stages. Stages are typed (processor, metric_extract, masker, router, …):

name: nginx-access-logs
description: Parse Nginx access logs and extract metrics
match:
  signal: logs
  conditions:
    - field: service_name
      op: "="
      value: "nginx"
stages:
  - type: processor
    name: parse_nginx_log
    processor: regex_extract
    source_field: body
    pattern: '^(?P<client_ip>\S+) - (?P<user>\S+) \[[^\]]+\] "(?P<method>[A-Z]+) (?P<path>\S+) HTTP/[\d.]+" (?P<status>\d+) (?P<bytes>\d+)'
    target_fields:
      http.method: method
      http.target: path
      http.status_code: status
    on_parse_failure: keep_original
  - type: metric_extract
    name: extract_request_count
    metric_name: nginx_requests_total
    metric_type: counter
    value_field: "constant:1"
    dimensions: [http.method, http.status_code, service_name]

The shape differs from the file loader: files put a pipelines: list at the top level, while POST /api/v1/pipelines takes one definition object. GET /api/v1/pipelines wraps the list as {"status":"success","data":[…]}.

Recording rules#

↗

Not executed in v0.3.1. Recording-rule groups are validated and stored, but no ruler scheduler evaluates them, so no derived series is written. Treat the examples below as the schema a future release will execute.

Recording rules pre-compute an expensive query into a new metric. They are grouped Prometheus-style, either as a file with a top-level groups: list or, through the API, as a single group object:

name: http_service_aggregations
interval: 1m
rules:
  - record: service:http_error_rate:rate5m
    expr: |
      sum by (service_name) (rate(http_requests_total{status=~"5.."}[5m]))
        / sum by (service_name) (rate(http_requests_total[5m]))
    labels:
      aggregation: "rate5m"
    description: "HTTP 5xx error rate per service"
    retention_override_days: 90

GET /api/v1/recording_rules returns every stored group under {"status":"success","data":[…]}.

Troubleshooting#

SymptomCauseResolution
Metrics do not appear after configuring an SDKThe SDK is exporting to the wrong port or protocol.Confirm gRPC uses :4317 and HTTP uses :8080. Enable SDK debug logging.
400 Bad Request on an OTLP/JSON postattributes sent as an object instead of an array.Use [{"key": …, "value": {"stringValue": …}}].
413 Payload Too LargeThe batch exceeds ingest.max_body_size.Raise the limit, or reduce the Collector's send_batch_size.
ResourceExhausted over gRPC onlyHistorically, gRPC and HTTP disagreed on the size limit.Upgrade to v0.3.0 or later, where gRPC limits derive from the same setting.
A metric is missing from an instant queryIts timestamp is outside the 5-minute lookback window.Query with /api/v1/query_range, or resend with a current timestamp.
traces_service_* metrics are absentSpans are not server-kind, or no spans have been received.Send spans with "kind": 2.
Span stored but RED metrics are staleExpected under tail sampling if you assumed sampling was the cause.RED metrics are derived before sampling; check keep_errors and span kind instead.
Throughput collapses after enabling wal_sync_mode = "always"Every write now forces a sync.Use interval with a tuned wal_sync_interval_ms unless you need the stronger guarantee.
